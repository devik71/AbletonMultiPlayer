# Ableton Live Multiplayer

Шар синхронізації поверх Ableton Live, що дозволяє двом (і більше) продюсерам працювати
над одним проєктом одночасно з різних машин: спільна структура проєкту, спільні семпли,
живий аудіо-моніторинг одне одного. Не форк, не патч Live — тонкий зовнішній шар навколо
легальних точок розширення (Remote Script / Live Object Model).

## 1. Візія

Мета — не заміна DAW і не realtime-джем всередині самого Live (мережева фізика цього
не дозволяє на достатньому рівні якості). Мета — відчуття "сидимо в одній кімнаті, кожен
зі своєю машиною, підключеною до спільного мікшера": один спільний, синхронний стан
проєкту + можливість почути, що робить партнер, без відчутного лагу в *стані* (не в звуці).

Явно поза скоупом MVP:
- Синхронне відтворення аудіо всередині самого Live між машинами (заміщено окремими
  інструментами для живого джему — Jamulus / JackTrip / WebRTC).
- Більше двох гравців одночасно (архітектура сумісна, але MVP тестується на двох).
- Мобільні клієнти, веб-UI поза Mac.

## 2. Інваріанти

Речі, які не порушуємо ні за яких обставин:

- Кожен гравець завжди має локально повністю робочий проєкт Live. Мережа відвалилась —
  робота не зупиняється.
- Джерело правди для структури проєкту — **послідовний журнал подій** (event log), а не
  "живий" стан якогось одного клієнта.
- Порядок подій визначає **єдиний арбітр** (сервер-секвенсор), а не wall-clock час машин
  і не P2P consensus/CRDT. Свідоме спрощення, виправдане масштабом (2–N гравців, не тисячі).
- Undo — це нова подія в журналі (append), а не видалення/переписування історії.
- Аудіо ніколи не є носієм синхронізації стану проєкту — тільки семантичні події.
- Повнорозмірні семпли синхронізуються файлово (SSH-тунель), окремо від event log.

## 3. Потоки даних — три труби

Кожна труба має власну фізику вимог, тому свідомо не об'єднуються в один протокол.

| Труба | Що несе | Транспорт | Пріоритет |
|---|---|---|---|
| **State sync** | треки, кліпи, параметри, транспорт | LOM ⇄ AbletonOSC (local) ⇄ Node-міст ⇄ WebSocket relay/sequencer | надійність і порядок > швидкість |
| **Sample sync** | повнорозмірні аудіофайли | filesystem watcher → git-annex/rsync over SSH (Tailscale/WireGuard тунель) | цілісність, не реалтайм |
| **Audio monitor/jam** | превью з браузера, потрековий live-listen, повний джем | Cue Output / multi-out routing → loopback capture → WebRTC (adaptive bitrate) | синхронність відчуття > якість звуку |

## 4. Межі відповідальності

- **Remote Script / Bridge** (Python, всередині процесу Live): читає/пише LOM, підписується
  на listeners для push-нотифікацій, серіалізує у OSC. Максимально тонкий і захищений —
  виняток тут може завалити сам Live.
- **Local Daemon** (Node.js, по одному на машину): OSC ⇄ WebSocket міст, file watcher,
  запис локального журналу, оптимістичне застосування власних дій.
- **Sequencer / Relay Server**: єдине джерело порядку подій. Зберігає journal, робить
  broadcast, snapshot + compaction, арбітраж локів.
- **File Sync Layer**: незалежний від сесії стану, живе своїм життям по SSH-тунелю.
- **Audio Layer**: незалежний процес (WebRTC), нічого не знає про event log.

## 5. Алгоритм — послідовна зміна кроків

Кожен гравець має власний локальний таймлайн дій. Сума двох (N) журналів, застосована
в єдиному порядку, і є спільний проєкт.

1. Дія гравця перетворюється в **семантичну подію** (не raw OSC, а домен-рівень:
   `SetClipParam`, `AddTrack`, `DeleteClip`, `DrawAutomationPoint(range)`...) з `author`,
   `local_seq` і payload.
2. Подія летить на сервер. Сервер присвоює монотонний **`global_seq`** і робить broadcast
   усім, включно з автором.
3. Кожен клієнт застосовує події **строго в порядку `global_seq`**. Це і є "наступна дія
   перемагає попередню": стан = результат послідовного застосування `journal[0..N]`.
4. Локально клієнт може оптимістично застосувати свою дію одразу (для відгуку без
   затримки) — але коли приходить офіційний `global_seq`, звіряється; якщо реальний
   порядок відрізнявся від локального припущення, робить replay з останнього snapshot.
5. **Гранулярність дії** — не весь трек, а конкретний параметр/кліп у конкретному
   часовому діапазоні. Список типів подій кінцевий і перелічуваний (`ClipLaunch`,
   `AutomationPointSet`, `DeviceParamSet`, `TrackCreate/Delete`, `SampleImport`,
   `MixerSet`...) — це і робить replay детермінованим.
   - **Лок = початок сесії дії, зняття лока = коміт.** Поки P2 малює automation lane
     (лок утримується), мікро-зміни (velocity точка за точкою) накопичуються тільки
     в локальному буфері — партнеру видно лише індикатор "P2 редагує", не потік кожної
     мікрозміни. На mouse-up/завершення дії буферизована дельта пакується в одну
     семантичну подію і йде в journal.
   - **Проміжні checkpoint-коміти** всередині довгої сесії лока (кожні кілька секунд) —
     щоб 5-хвилинна сесія малювання не загинула повністю при розриві мережі. Той самий
     механізм, що й періодичний clock-sync пакет (розділ 6) — суміщені задачі.
6. **Видалення/створення** — tombstone-підхід: видалений об'єкт лишається мертвим
   маркером у журналі; дії над неіснуючим об'єктом тихо ігноруються, а не застосовуються
   в порожнечу.
7. **Snapshot + compaction**: раз на N подій або за запитом нового учасника сервер зберігає
   повний знімок стану, журнал після нього обрізається. Реконект = snapshot + tail,
   не вся історія з нуля.
8. **Hash-chaining (tamper-evidence)**: кожна подія в журналі містить хеш попередньої
   події + свого payload. Не консенсус (не потрібен — сторони довіряють одне одному й
   спільному relay), а дешева перевірка цілісності: при реконнекті легко переконатись,
   що журнал не пошкоджений і нічого не випало. Повна історія лишається в холодному
   архіві навіть після snapshot-compaction — для undo, аудиту, "проходу назад" по сесії.

## 6. Clock sync (handshake)

Окремий механізм від `global_seq` — той визначає порядок подій і не залежить від
годинників машин. Clock sync потрібен для іншого: калібрування RTT/offset між
клієнтами, що живить (а) вікно оптимістичного replay, (б) UI-таймстемпи ("P2 зробив
це 2с тому"), (в) bar-boundary корекцію дрейфу аудіо-монітора через фазу Ableton Link.

- **Handshake** при конекті: класична NTP-подібна схема (`t0/t1/t2/t3` → offset + RTT).
- **Контрольний пакет** періодично (раз на N секунд, адаптивно частіше при рості
  RTT-варіації) тримає offset актуальним протягом сесії.
- Той самий пакет виконує подвійну роль — і clock-sync, і safety-checkpoint для довгих
  lock-сесій (розділ 5, пункт 5).

## 7. Фолбек-сценарії

- **Втрата зв'язку з relay**: локальна робота триває, journal буферизується локально;
  при реконнекті буфер відправляється, сервер вставляє в загальний порядок за
  `global_seq`, конфлікти — за правилами локів/tombstone вище.
- **Партнер без потрібного VST**: `Freeze` → `Flatten` → якщо неможливо (sidechain-роутинг
  блокує freeze) → ресемпл у аудіо. Файл летить через File Sync Layer як звичайний семпл.
- **Freeze/lock "завис"** (гравець вийшов з утриманим локом): timeout на неактивність
  (наприклад 5 хв) → авто-звільнення.
- **Мережі немає взагалі**: single-player mode — journal пишеться тільки локально,
  sync відкладається до відновлення зв'язку.
- **Ризикована дія** (додавання нового VST, імпорт унікального семпла — те, що може
  покласти DAW чи розсинхронити гравців): подія позначена `risky`-флагом тригерить
  звичайний Live-бекап (`Save a Copy`, timestamped `.als`) на машині-застосовувачі
  *перед* застосуванням. Rollback на рівні файлу — окремий, дешевий шар, незалежний
  від event log.

## 8. Моделі відмов

- Remote Script кидає виняток усередині процесу Live → Live може зависнути. Мітигація:
  максимально тонкий bridge-шар, вся логіка — поза процесом Live.
- UDP (OSC) губить пакети — малоймовірно на localhost (bridge ⇄ Live), але моніторити.
- WebSocket relay — single point of failure для сесії (state sync і lock-арбітраж
  зупиняються, якщо він впав). Прийнятно для двох гравців; при масштабуванні —
  розглянути failover.
- Розсинхрон версій (Remote Script під Live 12.1, партнер відкрив на 12.0) —
  **golden-версія на реліз**: одна протестована пара (версія Live, версія скрипта),
  явна перевірка версій при конекті.
- Дрейф аудіо-монітора — компенсується тільки на межі такту (bar boundary, через фазу
  Ableton Link), не миттєво — щоб корекція не була чутною посеред ноти.

## 9. Компроміси, які приймаємо свідомо

- **Сервер-секвенсор замість CRDT/P2P consensus** — простіше і надійне для 2–N гравців,
  ціна — single point of failure й потрібен relay (не чистий P2P).
- **Семантичний event log замість raw OSC replay** — трохи більше роботи на старті
  (треба спроєктувати схему подій), але портативно між версіями Live і дає
  undo-as-event безкоштовно.
- **LOM/AbletonOSC замість власного плагіна** — швидко й легально (community-maintained,
  не потребує Ableton SDK), ціна — неповне покриття API: freeze/export не скриптуються
  напряму, деякі nested-параметри (Groove, вкладені Rack-ланцюги) недоступні.
- **WebRTC для аудіо-моніторингу замість власного протоколу** — готовий adaptive
  bitrate/NAT traversal, ціна — менше контролю над деталями пайплайна.
- **Bar-quantized resync замість миттєвої корекції дрейфу** — трохи "гумове" відчуття
  при різкому дрейфі, але звучить музично коректніше за миттєвий стрибок.
- **Hash-chaining замість повноцінного blockchain/consensus** — довіра між гравцями і
  до spільного relay вже є за замовчуванням, тож майнинг/консенсус нічого не купує,
  тільки складність; hash-chain дає ту саму tamper-evidence практично безкоштовно.

## 10. MVP-скоуп (перша ітерація)

1. State sync: тільки `transport (play/stop/tempo)` + `clip launch/stop` через
   AbletonOSC ⇄ WebSocket relay з сервер-side sequencer.
2. Freeze-лок на об'єкт (soft-lock, без timeout-логіки на старті).
3. Sample sync: file watcher + rsync over SSH (Tailscale тунель), без git-annex поки що.
4. Audio monitor: відкладено на другу ітерацію.
