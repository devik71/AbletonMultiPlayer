# Ableton Live Multiplayer

Шар синхронізації поверх Ableton Live: двоє продюсерів працюють над одним проєктом
одночасно з різних машин. Не форк і не патч Live — тонкий зовнішній шар навколо
легальних точок розширення.

Візія і компроміси — [vision.md](vision.md), протокол — [docs/PROTOCOL.md](docs/PROTOCOL.md).
Перший прогін на двох машинах — [docs/FIRST-RUN.md](docs/FIRST-RUN.md).
Що ще не синхронізується — [docs/COVERAGE.md](docs/COVERAGE.md).
Довідник LOM для розробки — [.claude/skills/ableton-lom](.claude/skills/ableton-lom/LOCAL-NOTES.md)
(вендорена копія, карта а не ґрунт — межі довіри в LOCAL-NOTES).

> Проєкт не афілійований з Ableton і не містить їхнього коду. Взаємодія з Live
> йде виключно через задокументовані точки розширення — Remote Script і
> Live Object Model.

**Поточна версія: 0.19.0-dev — нерелізна.** Базова синхронізація перевірена на
парі машин із Live 12.3.8 і 12.3.5: транспорт і темп, запуск кліпів і сцен,
структура треків і сцен, мікшер звичайних/Return/Master треків, назви й кольори,
параметри девайсів (включно з вкладеними Rack chains), Session MIDI-кліпи з нотами.

А все, що додано поверх — повний знімок сету і його застосування, обмін знімками
між учасниками, присутність, follow, undo — **у живому Live ще не працювало
жодного разу**. Воно покрите юніт-тестами і наскрізним прогоном через емулятор
`fake-live`, який говорить тим самим протоколом, але не є Live: він не знає ні
про синхронні LOM-listener'и, ні про те, що Live сам «доправляє» виділення, коли
обʼєкт зникає. Суфікс `-dev` зникне після прогону на двох машинах.

Структура девайсів синхронізується: вставка, видалення й переїзд девайсів
через `insert_device`/`delete_device`/`move_device` з LOM 12.3. Перевірено на
живому 12.3.8 — усі три події проходять від Live через демон у журнал. Переїзд
іде **одним** `DeviceMove`, а не парою, бо пара перестворює девайс із дефолтів
і губить значення параметрів.

Arrangement має код і покриття емулятором, але живого підтвердження ще не має.
Тож два `.als` після спільної сесії поки не збігаються повністю.

## Як це влаштовано

```
Live (LOM)  ⇄  Bridge (Remote Script, Python, у процесі Live)
                    ⇅  JSON over UDP, localhost
               Daemon (Node, по одному на машину)
                    ⇅  JSON over WebSocket
                Relay / Sequencer (Node, один на сесію)
```

| Компонент | Відповідальність |
|---|---|
| `remote-script/AbletonMP` | LOM-listeners → події; застосування чужих подій до LOM. Максимально тонкий: виняток тут може завалити Live |
| `daemon` | UDP ⇄ WebSocket, реконект, буферизація, clock sync, синхронізація файлів, межі жесту для локів, присутність |
| `relay` | єдине джерело порядку: `global_seq`, hash-chain, журнал, broadcast, стиснення хвоста на join, арбітраж локів, присутність, undo |

Порядок подій визначає сервер-секвенсор, а не годинники машин. Стан проєкту —
результат послідовного застосування журналу, а не «живий» стан якогось клієнта.
Тому затримка каналу не ламає коректності: через інтернет усе працює так само,
як у локальній мережі, лише повільніше видно чужі дії.

## Що синхронізується

| Подія | Що несе |
|---|---|
| `TransportSet`, `TempoSet` | play/stop, темп (з дебаунсом) |
| `ClipLaunch`, `ClipStop`, `SceneLaunch`, `StopAllClips` | запуск і зупинка |
| `TrackCreate`, `TrackDelete`, `SceneCreate`, `SceneDelete` | структура |
| `MixerSet`, `TrackToggle` | мікшер звичайних/Return/Master треків (включно crossfader і cue) |
| `ObjectMetaSet` | назва і RGB-колір Track/Return/Master, Scene та Session Clip |
| `DeviceParamSet` | automatable-параметри девайсів звичайних/Return/Master треків, включно із вкладеними Rack chains |
| `ClipCreate`, `ClipDelete`, `ClipNotesSet` | Session MIDI-кліпи та ноти |
| `ClipLoopSet` | петля й маркери кліпу (одна подія на всі поля) |
| `TrackDuplicate` | дублювання треку разом із девайсами: партнер повторює дію |
| `DeviceInsert`, `DeviceDelete`, `DeviceMove` | структура девайсів: вставка стокового девайса за назвою, видалення, переїзд у межах треку і між треками |
| `DeviceLoad` | завантаження за uri через браузер — спадщина, лишена заради старих журналів |
| `ClipPropSet` | властивості кліпів: gain, warp, транспонування, launch mode, власний розмір такту — і для Session, і для лінійки |
| `ClipWarpSet` | warp-маркери audio-кліпів: увесь набір однією подією |
| `ChainMixerSet` | гучність, панорама й перемикачі ланцюга в раку — у Drum Rack це кожен пад |
| `SampleLoad` | семпл у слот Session, на пад Drum Rack або в лінійку (адреса — шлях у теці проєкту) |
| `SongPropSet` | розмір такту, квантизація запуску, тональність, петля Arrangement, punch |
| `SceneTimingSet` | темп і метр сцени — увесь блок перевизначень разом |
| `CueSet`, `CueDelete` | локатори в лінійці |
| `ReturnCreate`, `ReturnDelete` | набір Return-треків: від нього залежить, що означає index сенда |
| `ArrangementClipCreate/Move/Delete/NotesSet` | кліпи в лінійці та їхні ноти |
| `RegistryInit` | ідентичність об'єктів на старті сесії |

Треки і сцени адресуються **стабільними uuid**, не індексами. uuid зберігаються
всередині `.als` (`set_data`), тож дві машини, що відкрили копію того самого
файлу, отримують однакову ідентичність ще до будь-якого обміну.

Return Tracks і Master Track мають окремі aux-uuid. У `DeviceParamSet` вони явно
позначаються як `track.kind: "return"|"master"`, тому їх неможливо помилково
застосувати до звичайного треку з таким самим id.

Кліп адресується двома способами: сесійний -- парою (трек, сцена), бо власного
uuid у нього немає; кліп у лінійці -- власним uuid, бо сцен там не буває.
Ланцюги раків теж мають власні uuid, унікальні глобально.

Семпли з теки проєкту синхронізуються автоматично, окремим шаром — relay їх
не журналює, лише пересилає.

Поза журналом ходять інструменти спільної роботи: **локи** («p1 редагує Bass»),
**присутність** («p1 дивиться на Bass / Drop») і обмін знімками стану. Вони не
змінюють проєкт, тож у журналі їх немає — і це перевіряється тестами.

# Встановлення

Потрібні:

- **Node.js 18+** на кожній машині (`node -v`).
- **Ableton Live 11/12**.
- Max for Live — лише для вбудованих UI-патчів.
- OpenAI API key — лише для AI Chat; мультиплеєр працює без нього.

Windows — основна платформа: CI ганяє весь набір тестів на `windows-latest`.
macOS теж підтримується; шляхи для обох наведені нижче.

## 1. Код на обидві машини

```bash
git clone https://github.com/devik71/AbletonMultiPlayer.git
cd AbletonMultiPlayer
```

## 2. Проєкт — копіюється файлом

Це не крок «про всяк випадок», а умова роботи: uuid лежать **усередині** `.als`,
тож зібраний наново сет із такою самою структурою не підійде. Перешли партнеру
сам файл разом із текою проєкту, і подбай, щоб семпли лежали всередині неї
(див. «Межі» нижче).

Для першого тесту візьми чернетку, а не робочий проєкт: `follow`, `undo`
і застосування знімка пишуть у LOM.

## 3. Remote Script — на кожній машині з Live

**Windows:**

```powershell
cd remote-script
powershell -ExecutionPolicy Bypass -File .\install.ps1
```

`-ExecutionPolicy Bypass` потрібен, бо політика за замовчуванням блокує локальні
скрипти. Якщо User Library лежить не в `Документи\Ableton\User Library`, додай
`-UserLibrary '<шлях>'`. Для розробки є `-Symlink` (потребує адміна або Developer
Mode), для видалення — `-Uninstall`.

**macOS:**

```bash
REMOTE="$HOME/Music/Ableton/User Library/Remote Scripts"
mkdir -p "$REMOTE"
rsync -a --delete remote-script/AbletonMP/ "$REMOTE/AbletonMP/"
```

Для розробки зручніший symlink замість rsync:
`ln -s "$(pwd)/remote-script/AbletonMP" "$REMOTE/AbletonMP"` (стару копію спершу
прибрати).

Далі на обох машинах: **повністю закрити й відкрити Live**, потім
`Preferences → Link/Tempo/MIDI → Control Surface → AbletonMP`.

> Правки Remote Script підхоплює **лише повний рестарт Live**. Перезавантаження
> сету переінстанціює Control Surface, але модуль лишається в `sys.modules`.

Лог bridge — перше місце, куди дивитись, якщо щось не так:

- Windows: `%APPDATA%\AbletonMP\bridge.log`
- macOS: `$TMPDIR/AbletonMP/bridge.log`

## 4. Relay — одна машина на сесію

```bash
cd relay
npm install
npm start
```

Слухає `ws://0.0.0.0:19870`. Windows при першому запуску спитає про фаєрвол —
дозволь **приватні мережі**. Вхідний порт потрібен лише машині з relay; другій
достатньо вихідної зв'язності.

Журнали сесій — у `relay/journals/<session>.jsonl`.

## 5. Daemon — на кожній машині

```bash
cd daemon
npm install
node index.js --author p1 --session jam --relay ws://127.0.0.1:19870
```

На другій машині — той самий рядок, але `--author p2` і `--relay` з адресою
машини, де крутиться relay:

```bash
node index.js --author p2 --session jam --relay ws://192.168.3.18:19870
```

- `--author` має бути **різним** у гравців: relay дедуплікує події по парі
  `(author, lseq)`.
- `--session` має бути **однаковою** і прив'язана до конкретного проєкту: під
  однією сесією має відкриватись один і той самий `.als`.
- `--project <шлях>` — якщо сет ще не збережено і теку не вивести автоматично.
- Ще є `--token`, `--state-dir`, `--udp-in`, `--udp-out`.

Вікно daemon — це водночас пульт керування (див. «Команди daemon»), тож тримай
його відкритим.

## 6. Перевірка, що все зійшлось

1. У вікні daemon: `bridge підключився: Live …, script 0.19.0-dev` і `relay: head=…`.
2. Один із bridge створює реєстр, другий приймає — у лозі `реєстр прийнято`.
3. Відкрий `http://<relay-host>:19870/health` — там мають бути обидва гравці,
   їхні IP, версії Live і скрипта.
4. Крутни фейдер на одній машині — на другій він має поїхати.

## 7. Зупинка

Штатно — **`Ctrl+C` у вікні процесу**. Relay при цьому прощається з клієнтами
кодом 1001, тож daemon бачить штатне закриття і йде у звичайний реконект, а не
в обрив. Порядок зупинки не має значення: журнал на диску вже консистентний
після кожної події.

Remote Script живе всередині Live і зупиняється разом із ним. Щоб вимкнути його
не виходячи з Live: `Preferences → Link/Tempo/MIDI → Control Surface → None` —
bridge надішле `bye`, і daemon це побачить.

### Нескінченні «підключаюсь до …» — це не зависання

Коли relay недоступний, daemon **навмисно** повторює спроби з паузою, що росте
до 10 с, і пише про це в лог. Локальна робота при цьому триває, а події
накопичуються в буфері й підуть, щойно звʼязок відновиться. Тобто це штатна
поведінка, а не збій — якщо relay сьогодні не потрібен, daemon треба просто
зупинити.

### Якщо вікна немає або воно повертається

Ні daemon, ні relay не мають автозапуску й не перезапускають себе — у їхньому
коді немає ні `spawn`, ні `exec`. Тож вікно, що зʼявляється знову після
закриття, створює щось зовнішнє: WMI-трюк для SSH (нижче), ярлик в автозавантаженні
або завдання планувальника.

Знайти процес разом із його командним рядком:

```powershell
Get-CimInstance Win32_Process -Filter "Name='node.exe'" |
  Select-Object ProcessId, CommandLine | Format-List
```

Зупинити конкретний (з деревом дочірніх — разом із вікном `cmd.exe`):

```powershell
taskkill /PID <PID> /T /F
```

`taskkill /IM node.exe /F` теж працює, але вбʼє **всі** Node-процеси в системі,
не лише наші.

Хто його відроджує — видно за батьківським процесом і списками автозапуску:

```powershell
Get-CimInstance Win32_Process -Filter "ProcessId=<PID>" | Select-Object ParentProcessId
Get-CimInstance Win32_StartupCommand | Select-Object Name, Command, Location
Get-ScheduledTask | Where-Object TaskPath -notlike '\Microsoft*' | Select-Object TaskName, State
explorer shell:startup
```

# Гра через інтернет

Мережа не має бути спільною. Найпростіший шлях — **Tailscale**: на обох машинах
поставити, `tailscale up`, увійти одним акаунтом. Далі дізнатись адресу машини
з relay:

```powershell
tailscale ip -4        # виду 100.x.y.z
```

і вказати її в `--relay ws://100.x.y.z:19870`. З MagicDNS можна просто ім'ям
машини: `ws://mishanya-pc:19870`.

Якщо партнер висне на `підключаюсь до…`, найімовірніша причина — фаєрвол на
машині з relay: Tailscale-адаптер класифікується окремо, і дозволу «приватні
мережі» може не вистачити. Від адміністратора:

```powershell
New-NetFirewallRule -DisplayName "AbletonMP relay" -Direction Inbound -LocalPort 19870 -Protocol TCP -Action Allow
```

`tailscale status` покаже `direct` або `relayed`. У другому випадку трафік іде
через сервери Tailscale — помітно повільніше, і передача великих семплів стає
відчутною (див. «Межі»).

## Токен

Relay за замовчуванням відкритий: хто дістав до порту, той у сесії — може
комітити, вичитати весь журнал і забрати `pull`-ом повний стан проєкту.
У закритому tailnet це прийнятно, але токен коштує один рядок:

```powershell
# машина з relay
$env:MP_RELAY_TOKEN = 'довгий-випадковий-рядок'
npm start
```

```powershell
# кожен daemon
node index.js --author p2 --session jam --relay ws://100.x.y.z:19870 --token довгий-випадковий-рядок
```

Згенерувати: `node -e "console.log(require('crypto').randomBytes(24).toString('base64url'))"`.

Правило одне: **або токен є в обох, або в жодного**. Половинчастий стан —
найчастіша причина «чомусь не конектиться». При розбіжності relay пише
`join відхилено: невірний токен` (без самого токена — він у логи не потрапляє),
а daemon — `relay error [bad_token]` і йде в реконект.

У PowerShell `$env:...` живе лише в поточному вікні. Щоб назавжди —
`setx MP_RELAY_TOKEN "..."` і **нове** вікно.

З токеном закривається і `/health`: `http://host:19870/health?token=...` або
заголовок `x-relay-token`.

# Команди daemon

Вікно daemon приймає команди з клавіатури:

| Команда | Що робить |
|---|---|
| `who` | хто на що дивиться просто зараз |
| `follow <author>` / `follow off` | вести власний вид за партнером |
| `undo [author]` | відкотити останню зміну — свою або партнерову |
| `state` | підсумок знімка свого сету з digest |
| `pull <author>` | забрати свіжий знімок партнера і вирівнятись по ньому |
- **`npm run preflight`** — усе, що можна перевірити без партнера: памʼять
  проєкту, чи той код крутить Live, і повний набір тестів. Зупиняється на
  першій поломці — сесія з партнером коштує двох людей.
- `status` — одним екраном: звʼязок із relay, версія й **хеш коду** bridge,
  скільки типів подій він уміє, хто в сесії, чи є невідправлені події,
  скільки семплів у теці проєкту, digest останнього знімка.
  Під час прогону парою це відповідь на «у нас усе гаразд?» без читання лога.
- `diff <author>` — **порівняти** свій стан із чужим, нічого не змінюючи.
  `pull` тягне чужий знімок і застосовує його; `diff` лише називає
  розбіжності. Діагностика не має чіпати те, що діагностує.
| `apply [файл]` | вирівнятись по знімку з файлу |
| `refresh` | перезняти власний стан |

`follow` призупиняється, щойно ти клацнеш сам, і мовчить, поки транспорт грає
з озброєним треком — виділений трек вирішує, куди йде MIDI з клавіатури.

`pull` закриває сценарій «приєднався до сету, який бачу вперше»: партнер віддає
свіжий стан, ти вирівнюєшся по ньому, і в журнал при цьому нічого не йде.
Чого бракує саме тобі — daemon надрукує списком («немає девайса Serum на треку
Bass») і покладе повністю у `daemon/state/<author>.<session>.missing.json`.

# Max for Live

## Multiplayer Status

```text
m4l/AbletonMP Multiplayer Status.maxpat
m4l/abletonmp_multiplayer_status.js
```

Опитує `/health` кожні ~2 секунди і показує сервер, кімнати, онлайн-гравців з IP
і версіями, скільки дій зробив кожен author, розподіл подій за типами, секції
`editing now:` (локи) і `looking at:` (присутність).

Для віддаленого relay у полі Relay вказати `http://<relay-ip>:19870`; поле Room
можна лишити пустим або вписати конкретну `--session`. Якщо relay під токеном —
надіслати в js-об'єкт повідомлення `token <рядок>`, інакше буде `Token required`.

## AI Chat

```text
m4l/AbletonMP AI Chat.maxpat
m4l/abletonmp_chat.js
```

Remote Script піднімає authenticated localhost UI/API на `http://127.0.0.1:19847/`.
Відкрити `.maxpat` у Max, перевірити що `.js` лежить поруч, далі
`File → Save As...` як `.amxd` у User Library.

Ключ OpenAI потрібен лише для цього. Поклади його одним рядком у
`~/.abletonmp/openai_api_key` або біля Remote Script — обидва шляхи закриті
`.gitignore`. Токен локального chat API створюється автоматично
в `~/.abletonmp/chat_token`.

# Тонке налаштування relay

Усе через змінні оточення; за замовчуванням чіпати нічого не треба.

| Змінна | Типово | Навіщо |
|---|---|---|
| `MP_RELAY_PORT` | 19870 | порт |
| `MP_RELAY_TOKEN` | — | токен; порожній = відкритий relay |
| `MP_HEARTBEAT_SEC` / `MP_STALE_SEC` | 15 / 45 | пінг і розрив мовчазних зʼєднань |
| `MP_SUBMIT_RATE` / `MP_SUBMIT_BURST` | 100 / 300 | стеля темпу подій на зʼєднання |
| `MP_COMPACT_JOIN` / `MP_COMPACT_AT` | 1 / 2000 | стиснення хвоста на join і журналу на диску |
| `MP_SESSION_IDLE_SEC` | 900 | вивантаження порожньої сесії з памʼяті |
| `MP_FSYNC` | 0 | чекати диска на кожній події |
| `MP_MAX_BUFFERED` | 16 МБ | розрив зʼєднання з тим, хто не встигає читати |

Цілісність сесії будь-коли перевіряється окремо:

```bash
node relay/verify.js <session>
```

Він звіряє власні хеші подій, повний ланцюг холодного архіву, збіг архіву
з живим журналом і checkpoint. Ненульовий код виходу означає проблему.

# Перевірка без Live

`daemon/tools/fake-live.js` говорить тим самим UDP-протоколом, що й Remote Script,
тож увесь ланцюг ганяється без DAW:

```powershell
npm test                   # 57 unit/hardening + 53 E2E-перевірки
node test/e2e.mjs          # лише E2E; E2E_VERBOSE=1 для повного виводу
```

Ручний прогін: підняти relay, потім по парі daemon + fake-live на різних портах.
Команди fake-live: `play`, `tempo 128`, `launch 1 2`, `scene 3`, `vol 1 0.5`,
`mute 0`, `addtrack`, `move 0 2`, `note 0 0 60 0 1 100`, `delnote 0 0 60 0`,
`delclip 0 0`, `device 0 0 1 0.75`, `device 0 3/1/0/0/0 0 0.9`,
`device return:0 0 0 0.5`, `device master 0 0 0.5`, `mix return:0 volume 0.5`,
`toggle return:0 mute`, `mix master crossfader 0.5`, `meta scene:0 name Intro`,
`meta clip:0:0 color 16755200`, `look 1 2`, `view`, `fullstate`, `state`.

`test/inject.mjs` кидає одну подію в relay від імені окремого учасника — зручно
перевіряти застосування в справжньому Live без другої машини. У PowerShell JSON
надійніше передавати через `$env:MP_PAYLOAD='{"bpm":135}'`, а потім
`node test/inject.mjs TempoSet`.

## Daemon через SSH на Windows

Windows OpenSSH тримає сесію в Job-об'єкті з `KILL_ON_JOB_CLOSE`, тож процес
помирає разом із SSH. Ні `Start-Process`, ні `schtasks` не рятують. Робочий
варіант — створити процес через WMI, бо він не стає нащадком викликача:

```powershell
Invoke-CimMethod -ClassName Win32_Process -MethodName Create -Arguments @{
    CommandLine = 'cmd.exe /c "C:\Users\<user>\run-daemon.cmd"'
}
```

Логи daemon читати з `Get-Content -Encoding UTF8`, інакше кирилиця побита.
Якщо кирилиця побита прямо в консолі — це стара `cmd.exe`: `chcp 65001` або
Windows Terminal.

# Межі, про які варто знати

**Семпли поза текою проєкту не працюють.** Live за замовчуванням не копіює семпл
у проєкт — `.als` тримає посилання на оригінал, а в партнера цього шляху немає.
Виправити кодом не можна: `Collect All and Save` через LOM не викликається,
а `clip.file_path` доступний лише на читання. Daemon повідомляє, скільки семплів
поза проєктом, але зібрати їх має користувач.

**Великий семпл на повільному каналі рве зʼєднання.** Відправник вганяє всі чанки
файлу в сокет одним циклом; на LAN relay встигає їх віддавати, а на вузькому
каналі його буфер у бік отримувача переростає `MP_MAX_BUFFERED` (16 МБ) — і relay
розриває зʼєднання того, хто не встигає читати. Практично це помітно на файлах
більших за ~12 МБ. Тимчасовий обхід — підняти `MP_MAX_BUFFERED` або переносити
великі семпли вручну. Правильне розвʼязання (віконне підтвердження чанків) ще не
зроблене.

**Видалення файлів не поширюються.** Маніфест каже лише «що я маю», тож зниклий
семпл партнер віддасть назад. Прибирати треба на обох машинах.

**Локальний Ctrl+Z у Live не породжує події** — LOM не дає хука на undo-стек.
Натомість є власний `undo [author]`: він відкочує останню зміну новою подією
в журналі, тож історія лишається цілою, а скасування видно так само, як і саму
зміну. Відкотити можна лише те, що перезаписує адресу (фейдер, параметр, назву,
ноти); запуск кліпу чи створення треку — ні, і daemon скаже про це прямо.

**Групування треків не синхронізується.** LOM не вміє створювати групи взагалі,
тож партнер отримує попередження, а не фантомний трек. Треки всередині групи
лишаються спільними -- розходиться лише розкладка, і це видно у звіті знімка.

**Кліп, який зараз пишеться, не синхронізується** -- Live віддає для нього
заглушкову довжину. Подія йде один раз, коли запис завершився. Залупований
запис, що триває вічно, до партнера так і не потрапить.

**MIDI-синхронізація поки охоплює лише Session View.** Arrangement-кліпи,
audio clip creation, clip envelopes і довжина вже наявного
кліпу не спостерігаються. Для екстремально щільного MIDI один нотний тайл може
перевищити ліміт UDP-датаграми; bridge запише `datagram too large` у лог.

**Структура девайсів не синхронізується.** Звичайні, Return і Master треки мають
містити однакові Rack/Chain/device дерева. Невідповідний locator дає warning або
no-op, а не застосування до схожого девайса в іншому контейнері. Знімок стану
теж структуру не створює — лише вирівнює значення в наявній і друкує список,
чого бракує.

**Локи — порада, а не заборона.** Партнер бачить «p1 редагує Bass», але relay
нікого не блокує: одночасна зміна одного параметра вирішується за `global_seq` —
виграє останній. Заборона вимагала б відкату вже застосованої локально зміни,
а replay зі snapshot ще немає.

**Relay — single point of failure.** Журнал сесії існує лише на його машині;
разом із нею зникне й історія подій — і живий журнал, і холодний архів.

**Ідентичність сцен слабша за трекову.** `Track` уміє `set_data`, `Scene` — ні,
тож uuid сцен зберігаються мапою з позиціями і ламаються від переставляння сцен
між сесіями.
