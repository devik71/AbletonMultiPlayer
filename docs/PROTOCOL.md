# Протокол (фаза 1)

Три шари, два хопи. Bridge живе в процесі Live, daemon — окремий процес на тій самій
машині, relay — один на сесію.

```
Live (LOM)  ⇄  Bridge (Remote Script, Python)
                    ⇅  JSON over UDP, localhost
               Daemon (Node)
                    ⇅  JSON over WebSocket
                Relay / Sequencer (Node)
```

## 1. Bridge ⇄ Daemon — JSON over UDP

Один JSON-об'єкт на датаграму, UTF-8, без роздільників. Тільки localhost.

| Напрям | Порт |
|---|---|
| daemon слухає (bridge → daemon) | `19845` |
| bridge слухає (daemon → bridge) | `19846` |

### Bridge → Daemon

```jsonc
{"m":"hello","live":"12.3.8","script":"0.18.0","pid":1234,"features":["apply_ack","ai_chat","authenticated_lom","full_state"],"events":[...]}
{"m":"bye"}
{"m":"heartbeat","t":1723000000.0}
{"m":"event","type":"TransportSet","payload":{"playing":true},"lseq":7}
{"m":"snapshot","state":{"tempo":128.0,"playing":false,"tracks":[...]}}
{"m":"apply_ack","gseq":42,"ok":true}
{"m":"state_chunk","id":3,"seq":0,"total":4,"chars":118000,"data":"<фрагмент JSON>"}
{"m":"state_applied","id":1,"total":89,"ok":89,"failed":0,"errors":[]}
{"m":"view","view":{"track":{"id":"8fa1…"},"scene":{"id":"b7c2…"},"screen":"session","names":{"track":"Bass"}}}
{"m":"log","level":"warn","text":"..."}
```

### Daemon → Bridge

```jsonc
{"m":"apply","type":"TransportSet","payload":{"playing":true},"gseq":42}
{"m":"snapshot_request"}
{"m":"state_request"}
{"m":"state_apply","path":"…/p1.default.state.json","id":1}
{"m":"view_set","from":"p1","view":{…}}
{"m":"view_request"}
{"m":"registry_build"}
{"m":"registry_adopt","registry":{"tracks":[...],"scenes":[...],"aux_tracks":[...],"chains":[...]}}
{"m":"ping","t":1723000000.0}
```

У відповідь на `registry_build` bridge шле `{"m":"registry","registry":{...}}`.

`apply` — команда застосувати чужу (вже впорядковану сервером) подію до LOM.
Bridge при цьому оновлює last-known-value **до** запису в LOM, щоб власний listener
не породив ехо-подію (див. §4).

Daemon спочатку персистить чужий commit у `<author>.<session>.pending.jsonl` і
видаляє його лише після `apply_ack`. Черга не має ліміту в 500 подій і переживає
рестарт daemon до появи Live. Bridge без feature `apply_ack` підтримується в legacy-
режимі, але для нього UDP-відправка все ще вважається доставкою без підтвердження.

### Повний стан сету

Журнал -- це дельта поверх `.als`, який обидві машини відкрили з копії. Але
дельта нічого не каже про те, чи справді два сети зараз однакові, і не допоможе
тому, хто відкрив проєкт уперше. Для цього bridge уміє віддати **повний знімок**
усього, що він синхронізує.

Знімок не подія: у журнал він не потрапляє й порядку не має. Запитує його daemon
одразу після `hello`, якщо bridge оголосив feature `full_state`.

```jsonc
{"m":"state_request"}
{"m":"state_chunk","id":3,"seq":0,"total":4,"chars":118000,"data":"<фрагмент JSON>"}
```

Форма знімка -- ті самі адреси, що й у подіях: uuid треків і сцен, `chain_path`,
сигнатура девайса плюс `ordinal`. Тому знімок не вводить окремої мови опису
стану, і читається тими самими шляхами, якими застосовується подія.

```jsonc
{
  "version": 1, "script": "0.18.0", "live": "12.3.8", "at": 1723000000.0,
  "tempo": 128.0, "playing": false,
  "tracks": [{
    "id": "8fa1…", "idx": 0, "name": "Bass", "color": 16755200, "kind": "midi",
    "mixer": {"volume": 0.85, "panning": 0.0, "sends": [{"index": 0, "value": 0.25}],
              "mute": false, "solo": false, "arm": false},
    "devices": [{"chain_path": [{"id": "c1…"}],
                 "device": {"class_name": "Compressor2", "class_display_name": "Compressor", "ordinal": 0},
                 "parameters": [{"name": "Threshold", "ordinal": 0, "value": 0.5}]}],
    "clips": [{"scene": {"id": "df9…"}, "clip": {"length": 4.0, "name": "", "color": 16755200},
               "notes": [{"pitch": 60, "start_time": 0.0, "duration": 1.0, "velocity": 100}]}]
  }],
  "aux_tracks": [{"id": "a1…", "kind": "return", "idx": 0, "name": "A-Reverb", "mixer": {…}, "devices": [...]}],
  "scenes": [{"id": "df9…", "idx": 0, "name": "Intro", "color": 10053171}]
}
```

Обʼєкт без uuid у знімок не потрапляє: він однаково неадресовний для партнера.

**Чому чанками.** Знімок реального сету -- сотні кілобайт, а датаграма обмежена
65507 байтами (`link.py`), і bridge просто викинув би її з `datagram too large`.
Тому JSON ріжеться по 30000 символів, і чанки йдуть **порціями по тіках** (шість
на тік, ~10 тіків на секунду). Залп у сотню датаграм переповнив би приймальний
буфер daemon, і UDP тихо викинув би частину.

**Збірка** (`daemon/state.js`) віддає назовні тільки повний знімок. Порядок
чанків не має значення; новий `id` скасовує напівзібраний старий (доганяти його
немає сенсу -- свіжий однаково повніший); напівзібраний протухає за 15 с; довжина
склеєного JSON звіряється з оголошеною `chars`. Зібраний знімок лягає в
`<state-dir>/<author>.<session>.state.json`, а в лог іде підсумок із digest --
по ньому видно, чи розійшлись сети на двох машинах.

### Застосування знімка

Зворотний бік: узяти чужий знімок і вирівняти по ньому свій сет.

```jsonc
{"m":"state_apply","path":"…/p1.default.state.json","id":1}
{"m":"state_applied","id":1,"total":89,"ok":89,"skipped":0,"failed":0,"missing":[],"errors":[]}
```

Знімок передається **шляхом до файлу, а не датаграмами**: daemon і bridge живуть
на одній машині за побудовою, тож другий бік чанкування був би тут зайвою копією
коду.

Головне рішення -- **окремого шляху запису в LOM немає**. Знімок розкладається
на послідовність звичайних подій (`TempoSet`, `MixerSet`, `TrackToggle`,
`DeviceParamSet`, `ObjectMetaSet`, `ClipCreate`, `ClipNotesSet`) і застосовується
тим самим `_apply`, що й подія з журналу. Тому глушіння власного ехо, перевірка
адрес і тиха відмова на неіснуючий обʼєкт працюють без другої реалізації.

З цього випливає найважливіша властивість: **застосування знімка не породжує
подій**. Власні listeners заглушені, у журнал нічого не йде, партнер нічого не
бачить. Це локальне вирівнювання, а не дія користувача.

Операції йдуть порціями по тіках (12 на тік): знімок великого сету -- це тисячі
записів у LOM, і зробити їх одним махом означає підвісити Live.

**Що застосовується:** темп, назви й кольори треків, сцен і кліпів, мікшер
(включно з Return/Master), значення всіх параметрів девайсів, ноти Session-кліпів.
Порожній слот під ноти заповнюється -- `ClipCreate` нічого не руйнує.

**Що не застосовується ніколи:** структура. Треки, сцени й девайси не
створюються і не видаляються за знімком. Створити девайс через LOM узагалі
неможливо, а видалення треку знищило б чужу роботу назавжди -- ціна помилки
тут несиметрична. Тому знімок вирівнює значення в наявній структурі, а
розбіжність структур лишається видимою у звіті `state_applied`.
**Звіт про застосування** каже не лише скільки лягло, а й чого бракує:

```jsonc
{"m":"state_applied","id":1,"total":95,"ok":89,"skipped":6,"failed":0,
 "missing":[{"what":"track","id":"deadbeefcafe","count":3},
            {"what":"device","track":"Bass","device":"Serum","count":2},
            {"what":"parameter","track":"Bass","device":"Operator","name":"Cutoff","count":1}],
 "missing_more":0,"errors":[]}
```

Прогалини рахуються **окремою прохідкою** перед застосуванням кожної операції.
Це не дублювання: `_apply` на нерозвʼязану адресу мовчки виходить -- і це
правильно для журналу (tombstone-семантика, vision.md §5 п.6), але для знімка
означало б, що пропущене рахується як застосоване. Тому `ok` тепер означає
"справді записано", а `skipped` -- "адреси немає в цьому сеті".

Однакові прогалини склеюються: відсутній девайс із шістдесятьма параметрами --
це один рядок звіту з `count: 60`, а не шістдесят рядків. Різних рядків не
більше 50, решта -- у `missing_more`.

Daemon перекладає це в людський список і кладе повний у
`<state-dir>/<slug>.missing.json`:

```
знімок застосовано: 89 з 95, 6 пропущено. Бракує ось чого:
  · трек deadbeefcafe — такого немає (3 значень)
  · Bass / Serum — немає девайса (2 значень)
  · Bass / Operator — немає параметра Cutoff
```



Ноти ріжуться на регіони по 1024 (приймальний бік відхиляє payload із понад
4096 нотами цілком), і регіони тилують кліп впритул **починаючи з нуля**: регіон
не лише додає ноти, а й чистить те, що лежало в ньому раніше, тож без покриття
з нуля чужі ноти лишились би на місці.


### Обмін знімками

Знімок ходить між учасниками тією самою трубою, що й файли: relay його
**не журналює й не розуміє**. Це не подія і не має місця в порядку подій --
це вирівнювання станів.

```jsonc
{"m":"peer_state_request","to":"p1"}
{"m":"peer_state_chunk","to":"p2","id":314,"seq":0,"total":1,"chars":7385,"data":"…"}
{"m":"peer_state_error","to":"p2","text":"bridge не вміє віддати стан"}
```

Relay додає `from` і доставляє за `to` конкретному учаснику, а не в кімнату.

Той, у кого просять, **не віддає лежалий знімок**: він просить у свого bridge
свіжий і пересилає вже його. Інакше партнер отримав би стан, застарілий рівно
на стільки, скільки минуло від останнього `state_request`.

Знімок ріжеться по 200000 символів -- ліміт кадру relay 2 МБ, і великий сет
у нього не вліз би.

Той, хто просив, збирає чанки тим самим `StateCollector`, кладе результат
у `<state-dir>/<slug>.from-<author>.json` і одразу віддає bridge на застосування.
Файл лишається на диску: його можна застосувати ще раз командою `apply`.

**Незапитаний знімок ігнорується.** Чанки приймаються лише від того, у кого ми
самі щойно попросили: вирівнювання по чужому стану -- завжди свідома дія, і
партнер не має змоги нав'язати її. Якщо за 20 с відповіді немає, запит згасає.

## 2. Daemon ⇄ Relay — JSON over WebSocket

### Client → Relay

```jsonc
{"m":"join","session":"default","author":"p1","since":0,"proto":1,"token":"…"}
{"m":"submit","event":{"type":"TempoSet","payload":{"bpm":128},"author":"p1","lseq":7,"ts":1723000000.0}}
{"m":"ping","t0":1723000000.0}
{"m":"presence","view":{…},"following":"p2"}
{"m":"undo_request","author":"p1"}
{"m":"lock","object":"track:8fa1…","label":"Bass","ttl":30}
{"m":"unlock","object":"track:8fa1…"}
```

`since` — останній `gseq`, який клієнт уже має. Relay дошле хвіст.

### Relay → Client

```jsonc
{"m":"welcome","author":"p1","session":"default","head":{"gseq":41,"hash":"ab12..."},"peers":["p2"]}
{"m":"commit","event":{...,"gseq":42,"prev_hash":"ab12...","hash":"cd34..."}}
{"m":"peers","peers":["p1","p2"]}
{"m":"pong","t0":...,"t1":...,"t2":...}
{"m":"presence","list":[{"author":"p1","view":{…},"following":null,"age_sec":2}]}
{"m":"undo_proposal","type":"MixerSet","payload":{…},"of":{…},"from":18}
{"m":"locks","locks":[{"object":"track:8fa1…","label":"Bass","author":"p1","held_sec":3,"expires_in":27}]}
{"m":"lock_denied","object":"track:8fa1…","author":"p1","label":"Bass"}
{"m":"error","code":"proto_mismatch","text":"..."}
```

### Clock sync

Класична NTP-схема. `t0` — час відправки клієнтом, `t1` — прийому сервером,
`t2` — відправки сервером, `t3` — прийому клієнтом.

```
offset = ((t1 - t0) + (t2 - t3)) / 2
rtt    =  (t3 - t0) - (t2 - t1)
```

### Токен і темп подій

`MP_RELAY_TOKEN` на relay вмикає перевірку токена в `join`; daemon передає його
через `--token` або ту саму змінну оточення. Порожній токен -- відкритий relay,
як було досі: у домашній мережі це нормально, а в спільному Wi-Fi чи через
тунель будь-хто інакше може зайти в сесію і писати в журнал. Токени
порівнюються за SHA-256 через `timingSafeEqual` і не потрапляють у лог.

```jsonc
{"m":"join","session":"default","author":"p1","since":0,"proto":1,"token":"…"}
{"m":"error","code":"bad_token","text":"потрібен токен relay"}
```

Кожне зʼєднання має token bucket на `submit`: `MP_SUBMIT_RATE` подій/с
(100 за замовчуванням) зі сплеском `MP_SUBMIT_BURST` (300). Це захист журналу
від клієнта, що зациклився, -- звичайна робота цих меж не бачить, бо навіть
довгий жест дає сотні подій за секунди, а не тисячі за мить.

```jsonc
{"m":"error","code":"rate_limited","text":"не більше 100 подій/с"}
```

Відхилена подія **не втрачається і не вважається побаченою**: relay її не
комітить і не запамʼятовує пару `(author, lseq)`, а daemon тримає її в outbox
і повторює flush через секунду. Тому після паузи вона проходить тим самим
`lseq`, а не залипає як дублікат.

### Heartbeat і мертві зʼєднання

Обрив мережі (вимкнений Wi-Fi, приспана машина) не закриває TCP-сокет: без окремої
перевірки relay тримав би мертвого клієнта в `peers` і в `/health` до системного
таймауту, а партнер бачив би його онлайн. Раз на `MP_HEARTBEAT_SEC` (15 с) relay
шле ws-level ping кожному зʼєднанню. Ознакою життя вважається будь-який трафік
у зворотний бік — і автоматичний pong, і app-level `ping` daemon'а, який і так
іде кожні 15 с для clock sync. Тиша довша за `MP_STALE_SEC` (45 с) → зʼєднання
розривається, клієнт зникає з `peers`, партнери одразу отримують `peers`. Те саме
стосується зʼєднань, які так і не зробили `join`.

`/health` віддає на кожного клієнта `idle_sec` — скільки секунд від нього не було
жодного повідомлення.

### Локи

Лок каже партнеру «цей обʼєкт зараз редагують». Це **порада, а не заборона**:
relay нікому не відмовляє в `submit`, бо автор уже застосував зміну у своєму
Live, і відкат вимагав би replay з snapshot, якого ще немає (vision.md §5 п.4).
Конфлікт двох одночасних змін і далі вирішує `global_seq` — виграє остання.

У журнал локи не пишуться: це стан сесії, а не історія. Relay тут арбітр,
а не секвенсор, і `object` для нього — непрозорий рядок.

```jsonc
{"m":"lock","object":"track:8fa1…","label":"Bass","ttl":30}
{"m":"unlock","object":"track:8fa1…"}
```

```jsonc
{"m":"locks","locks":[{"object":"track:8fa1…","label":"Bass","author":"p1","since":…,"held_sec":3,"expires_in":27}]}
{"m":"lock_denied","object":"track:8fa1…","author":"p1","label":"Bass"}
```

`locks` — повний список кімнати, а не дельта: він летить усім після кожної
зміни і входить у `welcome`, тож новий учасник одразу бачить, що вже редагують.
Той самий список є в `/health`, звідки його показує M4L Status device.

Правила арбітражу:

- Лок належить **автору**, а не зʼєднанню: реконект того самого гравця
  підхоплює власний лок замість того, щоб упертись у нього як у чужий.
- Чужий лок неможливо ні перехопити, ні зняти — `unlock` від іншого автора
  тихо ігнорується.
- `ttl` (за замовчуванням `MP_LOCK_TTL_SEC`, 300 с; стеля 900 с) знімає лок,
  який «завис» (vision.md §7). Клієнт поновлює лок, поки жест триває.
- Коли гравець зникає з кімнати, його локи зникають разом із ним, не чекаючи
  TTL. Обрив мережі помічає heartbeat, а не системний таймаут TCP.

### Що вважається жестом

Межі жесту рахує daemon (`daemon/locks.js`), не bridge: усередині Live жест
виглядає як потік дрібних подій, і зводити його в одну сесію має процес, який
можна перезапустити (vision.md §4). Перша подія на обʼєкт бере лок, пауза
в потоці (1.5 с) його відпускає — пʼятихвилинне малювання automation тримає
один лок, а не блимає ним на кожній мікрозміні.

Лок беруть лише неперервні жести: `TempoSet`, `MixerSet`, `DeviceParamSet`,
`ClipNotesSet`. Дискретні дії (`ClipLaunch`, `TrackToggle`, `ObjectMetaSet`,
структурні події) миттєві — лок на них лише блимав би в чужому UI.

Обʼєкт лока грубіший за адресу події: весь трек, а не окремий параметр
(`track:<uuid>`, `return:<uuid>`, `master:<uuid>`, `clip:<track>:<scene>`,
`song:tempo`). Партнеру важливо «Bass зараз крутять», а не який саме кнопкою.
Назву для `label` daemon бере з реєстру сесії.

### Присутність

Локи кажуть «P2 редагує Bass», але не кажуть, **де P2 зараз**. Присутність
показує погляд: виділений трек, сцена, кліп у detail view і те, який екран
відкрито.

```jsonc
{"m":"presence","view":{"track":{"id":"8fa1…"},"scene":{"id":"b7c2…"},
                        "clip":{"track":"8fa1…","scene":"b7c2…"},
                        "screen":"session","names":{"track":"Bass"}},
 "following":"p2"}
{"m":"presence","list":[{"author":"p1","view":{…},"following":null,"age_sec":2}]}
```

Погляд **не змінює проєкт**, тож у журнал він не йде — це стан сесії, як локи.
Але на відміну від лока присутність **не має TTL**: вона істинна, поки людина
мовчки дивиться на трек, і таймаут стер би її посеред роботи. Замість TTL —
смерть разом із зʼєднанням (обрив ловить heartbeat) і явний `view: null`, коли
bridge замовк.

Relay тримає її станом сесії, а не пересилає трубою, з двох причин: M4L Status
device читає лише `/health`, а той, хто приєднався пізніше, має побачити
партнера одразу у `welcome`, не чекаючи наступного його руху.

**uuid обовʼязкові, назви — лише для показу.** Трек адресується так само, як
у `DeviceParamSet`: `{id}` для звичайного, `{id, kind}` для Return/Master.
Кліп — парою (track, scene), тож Arrangement-кліп неадресовний: тоді `clip`
відсутній, а `screen` пояснює чому. Назви relay обрізає до 64 символів.

Темп гаситься тричі: bridge коалесить зміни (0.15 с, стеля 0.5 с — не більше
двох повідомлень на секунду), daemon дедуплікує за підписом і тротлить до
250 мс, relay мовчки викидає частіше за 5/с — **без** відповіді помилкою,
інакше зламаний клієнт дістав би шторм назад.

Підпис виду навмисно не містить назв: перейменування треку не є рухом погляду,
і назва оновиться при наступному справжньому русі.

### Follow

`follow <author>` у терміналі daemon веде власний вид за партнером. Це єдине
місце, де bridge пише `song.view`.

```jsonc
{"m":"view_set","from":"p1","view":{…}}
{"m":"view_request"}
```

**Три петлі, які тут треба закрити:**

1. *Власний listener бачить те, що я щойно записав.* Запис `song.view.selected_track`
   кличе listener **синхронно, ще всередині `_apply_view`**. Тому прапорець
   `_suppress_view` і мітка часу виставляються **до першого запису**, а вікно
   `VIEW_ECHO_WINDOW` (0.5 с) лишається відкритим після: Live може доправити
   виділення асинхронно, якщо цільовий обʼєкт саме зник.
2. *Двоє слідують один за одним.* Daemon відмовляється йти за тим, у чиїй
   присутності стоїть `following: <я>` — саме для цього поле й їде на relay.
   Плюс клієнт не відсилає вид, що дорівнює виду лідера: це був би його ж рух,
   відбитий йому назад.
3. *Я слідую і сам клацаю.* Моя дія перемагає: будь-яка справжня зміна мого виду
   ставить follow на паузу на 5 с. Після власного `view_set` bridge присутності
   не шле, отже все, що прийшло від нього, — справжнє за побудовою.

**Follow призупиняється під запис.** Виділений трек у Live вирішує, куди йде
MIDI з клавіатури і що моніториться, тож поки транспорт грає і хоч один трек
озброєний, чужий вид не смикає виділення. Перемикання Session/Arranger не
робиться взагалі — це найгрубіше, що фіча могла б зробити під пальцями.

Нерозвʼязна адреса не ламає нічого: що зарезолвилось, те й ставиться, решта
лишається на місці — те саме tombstone-правило, що й для подій.

### Undo як подія

vision.md §2 оголошує це інваріантом: undo — це **нова подія в журналі**, а не
викреслювання старої. Історія лишається цілою, а скасування видно так само, як
і саму зміну — включно з тим, хто скасував.

```jsonc
{"m":"undo_request","author":"p1"}
{"m":"undo_proposal","type":"MixerSet","payload":{…},"of":{"gseq":42,"type":"MixerSet","author":"p1"},"from":18}
{"m":"undo_denied","author":"p1","text":"…"}
```

**Relay не комітить сам.** Він лише знаходить, яким значення було до останньої
дії автора, і віддає пропозицію клієнту — комітить її сам клієнт, своїм `lseq`.
Інакше relay зайняв би чужий номер, і справжня подія з тим самим `lseq` пізніше
загубилась би як дублікат.

**Що відкотне, вирішує та сама `supersedeKey`, що й стиснення.** Подія відкотна
рівно тоді, коли вона повністю перезаписує адресу. Тому структурні дії, запуск
кліпів і `RegistryInit` не потрапляють сюди самі собою — для них «попереднього
значення» не існує за побудовою, і відмова називає тип поіменно.

Друга причина відмови — адреса, якої в цій сесії ще ніхто не чіпав: тоді
попереднє значення лишилось у самому `.als`, і журнал його не знає.

Попереднє значення шукається спершу в памʼяті, а потім **у холодному архіві**:
стиснення журналу викидає саме перекриті події, тобто рівно ті, які потрібні
undo. Це друга причина, чому архів існує, крім аудиту.

У мультиплеєрі undo працює і на чужу дію: `undo <author>` у терміналі daemon.
Саме це й потрібно, коли партнер щойно зіпсував те, над чим ти працюєш.

### Зупинка relay

На `SIGINT`/`SIGTERM` relay закриває зʼєднання кодом 1001, і daemon бачить штатний
close замість обриву — далі звичайний реконект з backoff. Окремо зберігати нічого
не треба: checkpoint пишеться після кожного commit, тож head сесії вже на диску.

## 2b. File Sync Layer

Незалежний від event log (vision.md §4). Relay ці повідомлення **не комітить** —
просто пересилає учасникам сесії. Журнал про файли не знає, файли про журнал теж.

```jsonc
{"m":"files_manifest","files":[{"path":"Samples/Imported/kick.wav","size":40312,"hash":"a1b2…"}]}
{"m":"file_request","path":"Samples/Imported/kick.wav","to":"p2"}
{"m":"file_chunk","to":"p1","path":"…","seq":0,"total":3,"data":"<base64>"}
{"m":"file_ack","to":"p1","path":"…","seq":0}
```

Relay додає до пересланого `from: <author>`. Якщо в повідомленні є `to`, воно йде
тільки цьому учаснику: маніфест потрібен усій кімнаті, а запит і чанки -- ні.
Повідомлення без `to` (старий клієнт) і далі йде broadcast-ом.

### Вікно у вісім чанків

Спершу відправник вганяв усі чанки файлу в сокет одним циклом. На LAN relay
встигав їх віддавати, а на вузькому каналі його вихідний буфер у бік того,
хто не встигає читати, переростав `MP_MAX_BUFFERED` (16 МБ) -- і relay
розривав тому зʼєднання. Рвалось на файлах більших за ~12 МБ, тобто на
звичайному лупі з бібліотеки.

Тепер у польоті щонайбільше вісім чанків (півтора мегабайта): кожен
прийнятий чанк отримувач підтверджує `file_ack`, і рівно на стільки
зсувається вікно. Підтвердження важить вісімдесят байтів проти
чвертьмегабайтного чанка, тож підтверджується кожен -- економити тут
нема на чому, а відправник має точно знати, докуди партнер дочитав.

**Сумісність зі старим клієнтом задана поведінкою, а не прапорцем.** Партнер,
який про `file_ack` не знає, нічого не підтвердить; за пʼять секунд
відправник скаже про це в лог і дошле решту без вікна -- тобто рівно так,
як було досі. Гірше не стає нікому, а на двох свіжих машинах обмеження
зникає взагалі. Мовчання ж посеред передачі (тридцять секунд після
останнього підтвердження) -- це вже обрив: передача скидається, файл
поїде наново після наступного маніфесту.

### Що синхронізується і чому саме так

| Що | Режим | Причина |
|---|---|---|
| `Samples/**` | автоматично, двобічно | дані адитивні й на практиці незмінні — конфлікту немає за побудовою |
| `*.als` | **не синхронізується** | джерело правди для структури — журнал (vision.md §2); двобічний sync файлу створив би друге джерело, де переможця визначає час запису, а не `global_seq` |
| `.asd`, `Backup/`, `Ableton Project Info/` | не синхронізується | Live регенерує локально — у каналі це лише шум |

Транспорт — WebSocket, а не rsync over SSH, як передбачала vision.md §3. Причина
практична: SSH у тестовій парі однобічний (sshd лише на одній машині), і гнати
обидва напрямки через неї зробило б її особливою. Через relay обидві машини
рівні й тримають лише вихідні з'єднання — вхідних портів не треба взагалі.
Ціна: немає дельта-передачі, файл завжди йде цілком.

Тека проєкту виводиться зі `state.file_path`, який bridge бере з `song.file_path`.
Доки сет не збережено, шлях порожній — тоді потрібен `--project` вручну.

Сканування періодичне (10 с), а не через `fs.watch`: тека проєкту може лежати
в OneDrive, де події файлової системи приходять із затримкою або не приходять.
Кеш хешу інвалідується за розміром і `mtime`, тому зміна вмісту без зміни розміру
теж виявляється. Перед відправкою джерело повторно звіряє байти з маніфестом.
Одержувач приймає лише канонічні шляхи всередині `Samples/`, перевіряє розмір,
кількість чанків і SHA-256, а потім атомарно замінює файл через тимчасовий.

**Видалення не поширюються.** Маніфест каже лише «що я маю», тож зниклий файл
партнер не видалить — навпаки, при наступному обміні він оголосить, що файл у нього
є, і локальна сторона забере його назад. Прибирати семпл треба на обох машинах
одночасно. Осмислене видалення потребує tombstone для файлів, як у журналі для
об'єктів; поки цього немає.

## 3. Журнал і hash-chain

Relay пише `journal.jsonl` — один закомічений івент на рядок. Кожен івент:

```jsonc
{
  "gseq": 42,              // монотонний, присвоює виключно relay
  "prev_hash": "ab12...",  // hash попереднього івента ("" для gseq=1)
  "hash": "cd34...",       // sha256(prev_hash + canonical_json(body))
  "type": "TempoSet",
  "payload": {"bpm": 128},
  "author": "p1",
  "lseq": 7,               // локальна послідовність автора, для дедуплікації
  "ts": 1723000000.0,      // wall-clock автора, довідково; НЕ впливає на порядок
  "srv_ts": 1723000000.2   // wall-clock relay
}
```

`canonical_json` — ключі відсортовані, без пробілів. Поля `hash` немає в тілі,
яке хешується.

Дедуплікація на relay: пара `(author, lseq)` вже бачена → івент ігнорується
(ідемпотентний ре-сабміт після реконнекту).

Подія стає commit і розсилається клієнтам **лише після** успішного append у журнал.
Якщо при старті рядок не парситься або hash-chain розірваний, валідний префікс
лишається доступним для читання, але нові commit-и сесії блокуються. Причина
відображається як `journal_error` у `/health` — пошкоджений хвіст не маскується
новими записами.

Після кожного commit relay атомарно оновлює `<session>.checkpoint.json` із поточними
`gseq` і `hash`. На старті цей anchor звіряється з відповідним рядком журналу:
переписаний префікс блокує нові commit-и. Checkpoint може безпечно відставати, якщо
процес упав між append журналу та його оновленням — тоді він звіряється зі старим
префіксом і пересувається на актуальний head.

Це **integrity checkpoint, не snapshot стану Live**: він фіксує голову журналу,
а не стан сету. Обрізання журналу — окремий механізм, описаний нижче.

### Стиснення хвоста на join

Журнал на диску завжди повний -- це холодний архів для undo й аудиту
(vision.md §5 п.8). Стискається лише хвіст, який relay віддає клієнту після
`join`: із серії подій, де кожна наступна повністю перекриває попередню,
доїжджає остання. Правила -- у `relay/compact.js`.

Що дає стиснення: гравець, який приєднався до сесії з годинною історією, не
проганяє через Live тисячі проміжних положень фейдера і не перезапускає кліпи,
зупинені пів години тому.

Інваріанти, на які спирається клієнт:

- Результат -- **підпослідовність** хвоста. Події не синтезуються і не
  переписуються, `gseq` і `hash` лишаються оригінальними.
- **Остання подія хвоста не викидається ніколи**, тож `lastGseq` клієнта
  доходить рівно до `head`.
- **Невідомий тип події не згортається.** Старий relay не має права мовчки
  викинути подію, яку навчився слати новіший bridge.

Що згортається -- за адресою, яку подія перезаписує цілком:

| Тип | Ключ «останній перемагає» |
|---|---|
| `TempoSet`, `TransportSet` | глобальний |
| `MixerSet` | трек (з `kind`) + `param` + `index` |
| `TrackToggle` | трек (з `kind`) + `param` |
| `ObjectMetaSet` | обʼєкт + його uuid + `prop` |
| `DeviceParamSet` | трек + `chain_path` + сигнатура девайса + параметр |
| `ClipNotesSet` | Track+Scene uuid + **регіон** (різні регіони не перекриваються) |
| `ClipLaunch`, `ClipStop` | трек |
| `SceneLaunch`, `StopAllClips` | барʼєр: усе, що запускалось раніше, зникає |
| `ClipLoopSet` | кліп (Track+Scene **або** uuid у лінійці) |
| `ClipPropSet` | кліп + `prop` |
| `ClipWarpSet` | кліп -- увесь набір маркерів перезаписується цілком |
| `ChainMixerSet` | uuid ланцюга + `param` |
| `SongPropSet` | `prop` -- метр не перекриває тональність |
| `SceneTimingSet` | сцена -- увесь блок перевизначень разом |
| `CueSet`, `CueDelete` | час локатора: обидві події повністю визначають стан |
| `ArrangementClipMove` | uuid кліпа |
| `ArrangementClipNotesSet` | uuid кліпа + регіон |

`RegistryInit` і структурні події не згортаються: їхній ефект не описується
однією адресою. Це `TrackCreate/Delete/Duplicate`, `SceneCreate/Delete`,
`ClipCreate/Delete`, `DeviceInsert/Delete/Move`, `DeviceLoad`, `SampleLoad`,
`ReturnCreate/Delete`, `ArrangementClipCreate/Delete`.

Кліп адресується двома способами, і ключ згортання це враховує: сесійний --
парою Track+Scene, у лінійці -- власним uuid. `clip.id` має пріоритет над
`scene.id`, тож той самий трек і та сама властивість на різних кліпах
не перекривають одне одного.

`MP_COMPACT_JOIN=0` вимикає стиснення -- клієнт отримує повну історію, як
до його появи. `/health` показує `served_events` і `dropped_events` по сесії.

Ті самі правила застосовуються і до журналу на диску, коли він виростає
(див. «Стиснення журналу і холодний архів»).

### Стиснення журналу і холодний архів

Коли живий журнал переростає `MP_COMPACT_AT` подій (2000; `0` вимикає), relay
стискає його тими самими правилами, що й хвіст на join, і лишає на диску
підпослідовність, яка дає той самий стан. Якщо стиснення виграє менше за 20%,
воно не робиться взагалі.

Знімок стану Live для цього не потрібен, і це головне спрощення: базою для
нового учасника служить **сам `.als`**, який обидві машини відкрили з копії,
а журнал — лише дельта поверх нього. Тому «snapshot» тут може бути звичайною
послідовністю подій, яку вміє застосувати будь-який наявний bridge.

Порядок кроків обраний так, щоб падіння між ними не втратило історію:

1. Події, яких ще немає в архіві, дописуються в `<session>.archive.jsonl`.
   Архів append-only, його ніхто ніколи не обрізає — це та сама «повна історія
   в холодному архіві» з vision.md §5 п.8. Падіння одразу після цього кроку
   може повторити діапазон у файлі; читач розрізняє записи за `gseq`.
2. Пишеться checkpoint із `compacted`, `events`, `archived_through` і мапою
   `authors` (максимальний закомічений `lseq` кожного).
3. Живий журнал атомарно перезаписується стиснутим (tmp + rename).

Перевірка цілісності на старті різна для двох випадків:

- **суцільний журнал** — як і раніше: `gseq` іде без пропусків, кожна подія
  зчеплена з попередньою;
- **стиснутий** — дірки в `gseq` законні, тож перевіряється власний хеш кожної
  події, зчеплення сусідніх за номером подій і те, що подій не менше, ніж
  записано в checkpoint. Зникнення рядка ловить саме останнє. Повне зчеплення
  ланцюга лишається перевіряним за архівом (`relay/verify.js`), де історія ціла.

Дедуплікація мусить пережити стиснення: подія, викинута з живого журналу,
не сміє закомітитись удруге, якщо клієнт повторить її після рестарту. Тому
checkpoint зберігає максимальний `lseq` кожного автора, а relay відповідає на
такий ре-сабміт окремим повідомленням — повернути подію самою собою він уже
не може:

```jsonc
{"m":"ack","lseq":7}
```

Daemon на `ack` прибирає подію з outbox так само, як прибрав би на `commit`.

### Довговічність і перевірка

`appendFileSync` повертається, коли дані лягли в кеш ОС, а не на диск: після
зникнення живлення commit, який клієнт уже побачив, може зникнути. `MP_FSYNC=1`
змушує relay дочекатися диска на кожній події. Вмикається окремо, бо коштує
мілісекунди на подію; втрата процесу (не живлення) переживається і без нього.

Клієнт, який перестав читати сокет (заснув ноутбук), інакше роздував би буфер
відправки файловими чанками до самого спрацювання heartbeat. Понад
`MP_MAX_BUFFERED` (16 МБ) у буфері зʼєднання розривається.

`/health` показує IP, авторів і статистику, тож за наявності `MP_RELAY_TOKEN`
він теж під токеном: приймається заголовок `x-relay-token` або `?token=`.
Без токена -- `401` і жодних даних. Відкритий relay віддає `/health` як раніше.

Цілісність будь-коли перевіряється окремим скриптом:

```bash
node relay/verify.js <session> [--dir <тека журналів>]
```

Він звіряє власні хеші подій, повний ланцюг архіву, збіг архіву з живим
журналом і відповідність checkpoint. Повторений діапазон в архіві (падіння під
час стиснення) вважається нормою, якщо повторені записи ідентичні. Ненульовий
код виходу означає проблему.

### Health endpoint

`GET /health` на relay повертає JSON для моніторингу сесій. Крім `ok`, `proto`,
`head` і помилок журналу, відповідь містить присутність гравців, онлайн-клієнтів з IP/портом, версіями
Live/script/features, статистику дій по author і breakdown за типами подій. Цей
endpoint читає Max for Live device `AbletonMP Multiplayer Status.maxpat`; він не
змінює журнал і не є частиною realtime-протоколу синхронізації.

Сесія, у якій нікого немає довше за `MP_SESSION_IDLE_SEC` (900 с), вивантажується
з памʼяті разом зі своїм журналом і мапою дедуплікації. Наступний `join` підіймає
її з диска — з повною перевіркою hash-chain, як при старті relay. Тому в
`/health` є ще й `journals`: сесії, що лежать на диску, з розміром і ознакою
`in_memory`. Лічильники `served_events`/`dropped_events` при вивантаженні
обнуляються — вони про роботу процесу, а не про історію сесії.

`MixerSet` дебаунситься як `tempo` — рух фейдера це один жест, а не сотня кроків.
`TrackToggle` йде одразу: дебаунс дискретного перемикача лише додав би затримки.
Значення клампиться межами самого `DeviceParameter` (`p.min`/`p.max`) — вони різні
для гучності й send-ів, а вихід за межі кидає виняток.

Допустимі mixer-параметри залежать від типу треку:

- звичайний Track: `volume`, `panning`, `send`; `mute`, `solo`, `arm`;
- Return Track: `volume`, `panning`; `mute`, `solo`;
- Master Track: `volume`, `panning`, `crossfader`, `cue_volume`; без `TrackToggle`.

Для звичайного Track адреса лишається `{id}`; Return/Master використовують
той самий aux-простір `{id, kind}`, що й `DeviceParamSet`.


**Сенд возить uuid цільового Return-треку як контрольну суму.** Індекс
сенда -- це позиція, а не адреса: щойно в когось інша кількість або інший
порядок Return-треків, той самий `index: 2` означає **інший** ревер.
Найгірше тут те, що нічого не ламається помітно -- мікс просто звучить
не так, і знайти причину майже неможливо.

Тому поруч з індексом їде `return: {id}`. Приймальний бік звіряє: збіг --
застосовує, розбіжність -- відмовляє вголос і називає обидва uuid,
відсутність -- каже, що Return-треків у нього менше. Той самий принцип,
що з ординалом девайса: **індекс -- контрольна сума, не адреса**.

**Самі Return-треки синхронізуються** подіями `ReturnCreate` / `ReturnDelete`.
LOM додає Return лише **в кінець** (`create_return_track()` без аргументів),
тож порядок збігається за побудовою -- якщо обидві машини застосували ті самі
події. Контрольна сума при цьому лишається: вона ловить випадок, коли хтось
додав Return **руками**, поза журналом.

Зміна набору Return-треків зсуває **всі** сенди на **всіх** треках, тож після
неї дзеркало мікшера перебудовується цілком -- інакше перший же рух фейдера
порівнявся б зі значенням, що тепер належить іншому сенду.

### Межі кліпу, дублювання і завантаження девайсів

Три типи, додані після першого прогону на двох машинах.

**`ClipLoopSet`** несе всі пʼять полів однією подією навмисно: Live клампить
`loop_end` відносно `loop_start`, тож окремі події проходили б через невалідні
проміжні стани й псували пару. З тієї ж причини на прийомі спершу йде повна
валідація і лише потім записи, а порядок записів обирається за поточним станом
кліпу. Слухаються всі кліпи, не лише MIDI: audio-кліп ми не створюємо, але
якщо він приїхав із `.als`, його петлю синхронізувати корисно.

**`TrackDuplicate`** не передає вміст — партнер **повторює дію**
`duplicate_track` на тому самому джерелі, і Live сам робить йому копію
з девайсами й семплами. Дублювання виявляється по колізії uuid: Ctrl+D копіює
трек разом із `set_data`, тож копія приходить із ідентифікатором джерела, а
джерело живе. Ланцюги копії дістають однакові uuid на обох машинах через
детермінований `sha256(locator_key)` — нового протоколу для них не потрібно.
Джерела в партнера немає → порожній трек і гучне попередження: дія користувача
була, а відсутній трек ламає все, що на нього адресується.

**`DeviceLoad`** працює лише з дітьми першого рівня категорій `audio_effects`,
`instruments`, `midi_effects`. Межу задано вимірюванням: дампи браузера з двох
машин показали, що uri стокових девайсів (`query:AudioFx#Compressor`) ідентичні,
а вміст (`drums`, пресети) адресується локальними `FileId`, різними на кожній
машині. Резолв за uri, фолбек — точний збіг назви в тій самій категорії.
Айтема немає → рядок у звіті «Бракує ось чого», замінник не ставиться ніколи.

`load_item` кладе девайс у **виділений** обʼєкт, тож застосування рухає вид —
під тим самим глушінням, що й follow, і з тим самим guard'ом: поки транспорт
грає з озброєним треком, виділення не смикається. Але, на відміну від follow,
подію не можна пропустити, тож вона чекає в черзі до 60 секунд. Один девайс
за тік: завантаження важкого інструмента блокує Live на сотні мілісекунд.

Емісія автоматична: `_on_devices` порівнює дерево девайсів із попереднім
знімком і, якщо в **наявному** контейнері зʼявився рівно один девайс, шле
`DeviceLoad`. Будь-що складніше — дві появи, зникнення, перестановка —
глушить емісію цілком: видалення девайса події не має взагалі, тож
перенесення девайса між треками виглядає як «зникло там, зʼявилось тут»,
і сама лише поява дала б партнеру дубль. Новий контейнер (копія треку,
свіжий ланцюг) не рахується: його вміст уже приїхав із `TrackDuplicate`.

Фільтр на сам девайс суворий, бо з `Device` не читається uri: єдина ниточка
назад у браузер — `class_display_name`, і вона мусить дати **рівно один**
айтем першого рівня в усіх трьох категоріях разом. Плюс девайс має бути
голий: `name` дорівнює `class_display_name` (у пресета там назва пресета),
рак без ланцюгів, Drum Rack без заповнених падів. Інакше подія не йде —
бо пресет `Compressor/Warm Bus` має той самий `class_name`, що й голий
Compressor, і автоемісія тихо віддала б партнеру дефолт замість того, що
чує автор. Так це й формулюємо: **структуру дає `DeviceLoad`, значення —
знімок**; дірку закриє `pull`, а мовчки покладений не той девайс — ні.

У знімок `DeviceLoad` не входить ніколи: знімок не рухає чужий курсор,
а `load_item` фізично смикає `song.view`.

Сигнатура для діффу структури — трійка `class_name`/`class_display_name`/
`name`. Без `name` пресет не відрізнити від однойменного голого девайса
поруч, і вставку зарахувало б сусідові: партнер дістав би другий примірник
того, що в нього вже є. Перейменування девайса через це виглядає як
заміна — і теж глушить емісію, що правильно.

Застосування чужого `DeviceLoad` теж викликає `_on_devices`, тож на час
`load_item` виставляється `_suppress_struct` — без нього подія відбивалась
би назад по колу.

### Структура девайсів: Insert, Delete, Move

`DeviceLoad` лишається в `APPLY_TYPES` заради старих журналів, але новий код
його не емітить. Причина не в стилі: LOM 12.3 має `insert_device`, і він
міняє все, що робило `DeviceLoad` дорогим.

`browser.load_item` кладе девайс у **виділений** обʼєкт -- звідси черга на
60 секунд, глушіння виду і guard на час запису. `insert_device(name, index)`
бере індекс явно й виділення не чіпає, тож із трьох нових типів у черзі
лишаються тільки `DeviceInsert` і `DeviceMove`, і лише щоб залп із журналу
не підвісив Live завантаженням важких інструментів. `DeviceDelete` іде одразу.

**Адреса девайса -- `class_display_name`.** Не `class_name`: `insert_device`
на `"Eq8"` відповідає `not found`, на `"EQ Eight"` -- працює. Те саме поле ми
вже возимо в `DeviceParamSet`, тож нового словника не зʼявилось, а браузер
із його `uri` і локальними `FileId` більше не потрібен узагалі.

Дві відмови `insert_device` означають різне, і партнер має бачити різницю:

- `not found` -- назви ця інсталяція не знає: стороннє, пресет, помилка;
- `not available` -- назву Live знає, але девайса немає в **цій редакції чи
  бібліотеці**. Після того як зʼясувалось, що редакції в учасників можуть
  відрізнятись, це вже не теоретичний випадок.

**Емісія.** `_diff_devices` порівнює дерево з попереднім знімком і розрізняє
три випадки: одна поява -> `DeviceInsert`, одне зникнення -> `DeviceDelete`,
зникнення й поява **тієї самої сигнатури** -> переїзд. Усе складніше й далі
глушить емісію цілком: дві появи, перестановка трьох девайсів, видалення
разом зі вставкою іншого. Краще діра, яку закриє знімок.

Фільтр на голий девайс лишився, але тільки для вставки: `insert_device` уміє
лише стокову назву, тож пресет `Compressor/Warm Bus` приїхав би партнеру
дефолтом. Видалення й переїзд голизни не потребують -- за індексом
видаляється й переїжджає що завгодно. Тобто пресет тепер синхронізується
наполовину: створення ні, зникнення й переїзд так.

**Переїзд: один тип, а не пара.** `DeviceMove` міг би розкластись на
`DeviceDelete` + `DeviceInsert`, і код був би меншим на один обробник. Ціна
виміряна на живому 12.3.8: девайс перестворюється з дефолтів.

| | порядок | `Frequency` девайса |
|---|---|---|
| `song.move_device` | змінився правильно | **0.25 -- збереглась** |
| `delete` + `insert` | змінився так само | **0.899657 -- дефолт** |

Те саме при переїзді між треками, де втрата болючіша: девайс уже налаштований
під конкретну партію. Обидва шляхи лишились у коді під `ABLETONMP_DEVICE_MOVE`
(`move` за замовчуванням, `pair` -- альтернатива), щоб різницю можна було
переміряти, а не доводити. У режимі `pair` неголий девайс глушить емісію
цілком: саме лише видалення знищило б партнеру девайс без заміни.

Перемикач читається по-різному з обох боків навмисно: у bridge це змінна
оточення (режим -- рішення розгортання), у `fake-live` ще й команда `movemode`,
бо інакше перевірка другого режиму коштувала б окремої сесії з релеєм, демоном
і двома емуляторами заради одного прапорця.

`DeviceDelete` і `DeviceMove` несуть повну сигнатуру девайса не для адресації,
а для **звірки**. Індекс каже, що поїхало; сигнатура ловить те, що поїхало не
те. Без неї розбіжність станів стерла б партнеру чужий девайс мовчки.

### Arrangement

Чотири події. Створити кліп «з нічого» LOM не вміє ніколи -- є лише
`duplicate_clip_to_arrangement(джерело, час)`, -- тож приймальний бік
збирає тимчасове джерело в **порожньому слоті Session** і одразу його
прибирає. Звідси й єдина причина відмови: усі слоти треку зайняті.

```jsonc
{"type":"ArrangementClipCreate","payload":{
  "track":{"id":"…"},"start_time":8.0,
  "clip":{"id":"…","length":4.0,"name":"","color":9611263,"is_midi":true}}}

{"type":"ArrangementClipMove","payload":{
  "track":{"id":"…"},"clip":{"id":"…"},"start_time":16.0}}

{"type":"ArrangementClipDelete","payload":{"track":{"id":"…"},"clip":{"id":"…"}}}

{"type":"ArrangementClipNotesSet","payload":{
  "track":{"id":"…"},"clip":{"id":"…"},"region":{…},"notes":[…]}}
```

**Ноти йдуть окремо від створення** -- свідомо. Кліп в Arrangement може
містити тисячі нот, і якби вони їхали всередині `ArrangementClipCreate`,
один драг довгого кліпу заблокував би чергу партнера на секунди. Ціна --
кліп зʼявляється на мить порожнім. Регіони ті самі, що в `ClipNotesSet`.

`ArrangementClipMove` застосовується як **копія на нову позицію плюс
видалення старої**: прямого сеттера `Clip.start_time` немає. Привʼязка
uuid робиться до видалення -- якщо `delete_clip` упаде, uuid уже вказує
на кліп, який реально лежить на новому місці.

Емісія -- діфф лінійок перед праймінгом. **Переїзд розпізнається за тим,
що вижив сам обʼєкт `Clip`**: uuid той самий, змінився лише `start_time`.
Якщо Live обʼєкт перестворив, вийде пара видалення+створення -- партнер
усе одно збіжиться, просто кліп дістане новий uuid і ноти поїдуть заново.

Згортання: `ArrangementClipMove` має ключ `arrmove:<uuid кліпу>`, тож
серія рухів доїжджає останньою; `ArrangementClipNotesSet` -- ключ із
регіоном, як у Session. Створення й видалення -- структура, вони не
згортаються ніколи. Локи беруться на `arrclip:<uuid>`, спільний для
переїзду й нот того самого кліпу.

Знімок віддає для кожного треку `arrangement: [{id, start_time, end_time,
length, name, color, is_midi}]`. У `_state_to_ops` це **не** перетворюється
на операції: знімок структури не створює, і Arrangement тут не виняток.
Розбіжність натомість називається вголос через `_structural_gaps`.

Audio-кліпи цими подіями поки не створюються: `ArrangementClipCreate`
з `is_midi: false` відхиляється. Це межа **реалізації**, а не LOM --
проба на живому 12.3 показала, що `browser.load_item` у виділений слот
створює audio-кліп, а той далі йде в Arrangement тим самим
`duplicate_clip_to_arrangement`. Див. docs/COVERAGE.md, розділ про семпли.

`_structural_gaps` повідомляє три види розбіжності: кліп є в партнера й
немає в тебе, є в тебе й немає в партнера, і той самий кліп на різних
позиціях -- переїзд, якого ніхто не бачив. Лічильники `ok`/`skipped` не
чіпаються: це не «не вдалось застосувати», а «у нас різні лінійки».

Що показала проба LOM на 12.3 і що з цього випливає для наступної стадії:

| Операція | LOM |
|---|---|
| Створити | `Track.duplicate_clip_to_arrangement(clip, time)` -- джерелом годиться і Session-кліп, і сам Arrangement-кліп |
| Видалити | `Track.delete_clip(clip)` |
| Пересунути | прямого шляху немає (`Clip.start_time` без сеттера) -- копія на нову позицію плюс видалення старої |

Тобто створити кліп «з нуля» не можна ніколи: потрібне джерело. Для MIDI
це не перешкода -- джерело можна зібрати в порожньому слоті Session
і одразу прибрати. Для audio-кліпів шлях інший і теж перевірений:
семпл вантажиться в слот через `browser.load_item`, а вже той кліп
дублюється в Arrangement.

### Локатори

```jsonc
{"type":"CueSet","payload":{"time":32.0,"name":"Drop"}}
{"type":"CueDelete","payload":{"time":32.0}}
```

**Адреса -- час, і це не спрощення.** `CuePoint.time` доступний лише на
читання, `set_data` в нього немає, а два локатори не бувають на одній
позиції. Отже час і **є** ідентичність. Пересунути локатор не можна
взагалі -- у Live це видалити й поставити заново.

Обидві події ділять ключ згортання `cue:<time>`, і це коректно в обидва
боки: кожна з них повністю визначає стан за своєю адресою, тож
`CueSet`+`CueDelete` згортається у видалення, а `CueDelete`+`CueSet` --
у створення.

**Застосування чекає на паузу.** `set_or_delete_cue()` працює лише
в **поточній** позиції -- іншого шляху LOM не дає. Тобто поставити локатор
у партнера означає на мить зрушити його плейхед. Під час відтворення це
чути, і чужий локатор -- не варта того причина, щоб перебити людині гру.
Подія чекає в черзі до пʼяти хвилин.

### Спільний плейхед: чому його немає

`current_song_time` записується, тож технічно синхронізувати позицію можна.
Ми цього не робимо, і причин три.

Під час відтворення вона змінюється **щотіку** -- у журналі це потік,
а не події. Далі: позиція під час гри у кожного **своя**, і це не дефект,
а те, заради чого проєкт існує -- «кожен грає своє». І нарешті: примусово
зрушити чужий плейхед означає перебити людині виконання.

Осмислена частина цієї ідеї -- не позиція як стан, а **де партнер зараз
стоїть**. Це присутність, а не журнал: той самий канал, що вже показує,
на що людина дивиться, і той самий `follow`, який за нею веде. Локатори
при цьому лишаються в журналі, бо вони -- структура документа: партнер
без них бачить голу лінійку.

> **Обидві події -- і `ClipPropSet`, і `ClipWarpSet` -- адресують кліп
> двома способами.** Сесійний кліп власного uuid не має, тож він
> адресується парою (трек, сцена). Кліп у лінійці навпаки: сцен там не
> буває, зате uuid є. Одна подія вміє в обидва -- інакше audio-кліп
> у лінійці лишався б без gain і warp, тобто саме там, де warp
> найпотрібніший.

### Мікшер ланцюга в раку

```jsonc
{"type":"ChainMixerSet","payload":{
  "chain":{"id":"…"},"param":"volume","value":0.37}}
```

`volume`, `panning`, `mute`, `solo`. Адреса -- **uuid ланцюга**, той самий,
що вже адресує девайси всередині нього: ланцюги унікальні глобально, тож
ні трек, ні шлях у payload не потрібні.

**У Drum Rack кожен пад -- це ланцюг.** Тобто гучність і панорама пада --
частина звучання, а не оздоблення, і досі вони не їхали взагалі: ми
синхронізували девайси ВСЕРЕДИНІ ланцюга, але не сам ланцюг.

Неперервні величини дебаунсяться, перемикачі йдуть одразу. Згортання за
`chain:<uuid>:<param>` -- гучність пада не перекриває його ж панораму,
а різні пади не заважають одне одному. Лок береться на ланцюг цілком.

Ланцюга з таким uuid немає -> подія мовчки не діє: рак могли видалити,
доки подія летіла.

### Warp-маркери

```jsonc
{"type":"ClipWarpSet","payload":{
  "track":{"id":"…"},"scene":{"id":"…"},
  "markers":[{"beat_time":0.0,"sample_time":0.0},
             {"beat_time":64.0,"sample_time":38.4}]}}
```

**Увесь набір разом, а не маркер за маркером.** Маркери описують
ВІДОБРАЖЕННЯ файлу на долі: половина набору -- не «майже правильно»,
а інший ритм. Тому подія несе повний список, а згортання за
`warp:<track>:<scene>` лишає останній.

`sample_time` -- **секунда у файлі**, не кадр (виміряно: маркер на 64-й долі
при 100 bpm дає 38.4). Пара портативна, бо описує той самий файл, а не
позицію на диску -- і саме тому працює разом із `SampleLoad`.

Застосування спершу **додає**, потім прибирає зайве: кліп без жодного
маркера Live не приймає, і порожній проміжний стан коштував би нам усього
набору. Останній маркер прибрати не дає сам Live -- це не помилка.

На MIDI-кліпі warp-маркерів немає взагалі: подія відхиляється як різниця
типів, а не як збій.

### Властивості кліпів

```jsonc
{"type":"ClipPropSet","payload":{
  "track":{"id":"…"},"scene":{"id":"…"},"prop":"gain","value":0.42}}
```

Тринадцять властивостей поза межами кліпу: `gain`, `pitch_coarse`,
`pitch_fine`, `warping`, `warp_mode`, `ram_mode`, `muted`, `legato`,
`velocity_amount`, `launch_mode`, `launch_quantization`, а також ВЛАСНИЙ
розмір такту кліпа -- `signature_numerator` і `signature_denominator`.
Він окремий від розміру пісні й визначає сітку кліпу, тобто те, як читаються
позиції нот усередині нього. Знаменник, як і в пісні, приймається лише
степенем двійки.

Частина існує **лише в audio-кліпів**. На MIDI їх просто немає, і спроба
записати -- не помилка партнера, а різниця типів: вона дає попередження,
а не збій. Для аудіо ж це половина звучання: досі семпл у партнера грав
інакше, ніж в автора, бо ми не возили ні підсилення, ні warp, ні
транспонування.

Згортання за `clipprop:<track>:<scene>:<prop>` -- своя адреса на пару
(кліп, властивість). `gain` тягнуть мишею, тож серія доїжджає останньою,
але `gain` не перекриває `warp_mode`.

Лок натомість береться на **кліп цілком** (`clip:<track>:<scene>`, той
самий обʼєкт, що в нот і меж): людина крутить один кліп, і показувати
«зайнято» правильніше про нього, а не про окреме поле.

Кліпа за адресою немає -> подія мовчки не діє. Це та сама tombstone-
семантика, що всюди: кліп могли видалити, доки подія летіла.

### Скарга авторові: apply_gap

```jsonc
{"m":"apply_ack","gseq":42,"ok":true,"type":"DeviceParamSet","gap":{"what":"parameter","name":"Morph"}}
{"m":"apply_gap","from":"p2","gseq":42,"type":"DeviceParamSet","gap":{…}}
```

Подія доходить, приймальний бік чесно її пропускає (адреси не існує), і про
це знає лише **його** лог. Автор крутить ручку, у партнера нічого не
рухається, причини не бачить ніхто. Це найдорожчий різновид розсинхрону, бо
він не схожий на поломку.

Живий приклад, виміряний на парі 12.3.5 + 12.4.3: Ableton перейменувала
`Morph` на `Filter Morph`, і параметр перестав знаходитись.

Тепер приймальний бік рахує прогалину **до** застосування -- тією самою
`_op_gap`, що вже описує пропущене для знімків, -- і кладе її в `apply_ack`.
Демон пересилає її relay-ю, relay знаходить **автора події за gseq** і шле
скаргу саме йому. Не всій кімнаті: решті вона нецікава й лише шумить.

Однакові скарги в автора склеюються -- тягнення ручки дає їх десятками,
а новина в них одна.

Це не робить подію застосованою. Tombstone-семантика лишається: адреси
немає -- дії немає. Змінилось інше: тепер про це знають обидва.

### Стан девайса повз параметри

```jsonc
{"type":"DeviceStateSet","payload":{
  "track":{"id":"…"},"chain_path":[{"id":"…"}],
  "device":{"class_name":"InstrumentVector","class_display_name":"Wavetable","ordinal":0},
  "prop":"oscillator_1_wavetable_index","value":3}}
```

`DeviceParamSet` возить будь-який `DeviceParameter` будь-чого -- він не знає
про конкретний девайс, і тому параметри покриті всі. Але частина звучання
живе не в параметрах.

Аудит на живому 12.3.5 ([device-audit.md](device-audit.md)) показав: із 85
стокових девайсів **68 не мають нічого понад `parameters`**. Решта тримає
в звичайних властивостях те, без чого сет звучить інакше:

| Девайс | Що саме |
|---|---|
| Wavetable | яка таблиця в кожному осциляторі, unison, маршрутизація фільтра |
| Simpler | режим програвання, slicing, multi-sample, голоси |
| Hybrid Reverb | який завантажений IR |
| Drift | уся матриця модуляції |
| Meld | вибраний engine |
| Spectral Resonator, EQ Eight, Roar, Shifter | режими |
| CC Control | на що мапиться кожен CC |
| раки | яка варіація підсвічена |

**Перелік плоский, без таблиці «клас -> властивості».** Імена достатньо
характерні, щоб не перетнутись, а наявність перевіряється через `hasattr`:
девайс, у якого властивості немає, просто не потрапляє ні в підписку, ні
в знімок. Додати девайс потім -- рядок у переліку, а не гілка в коді.

**Значення записується й перечитується.** Live мовчки клампить те, що поза
діапазоном: виміряно, що `poly_voices = 7` стає іншим числом. Тому дзеркало
після запису оновлюється тим, що вийшло насправді, -- інакше наступна зміна
не помітилась би.

Варіації раків тут -- дрібниця, і варто сказати чому. Значення макросів це
`DeviceParameter`, тобто звучання перемикання доїжджає й без нас. Сюди йде
лише те, яка варіація підсвічена.

Згортання за `devstate:<трек>:<ланцюги>:<девайс>:<властивість>`. Лок -- на
девайс цілком, спільний із `SamplePropSet`.

Девайса немає або в нього немає такої властивості -> подія мовчки не діє,
а автор дізнається про це через `apply_gap`.

### Маркери й підсилення семплу

```jsonc
{"type":"SamplePropSet","payload":{
  "track":{"id":"…"},"chain_path":[{"id":"…"}],
  "device":{"class_name":"OriginalSimpler","class_display_name":"Simpler","ordinal":0},
  "prop":"start_marker","value":20000}}
```

У Simpler дві різні речі, і плутати їх дорого. **Ручки** `S Start`, `S Length`,
`S Loop On`, `S Loop Length`, `S Loop Fade` -- це звичайні `DeviceParameter`,
і вони їдуть `DeviceParamSet`-ом як усе інше. А **маркери на хвилі** живуть
в окремому обʼєкті `device.sample` і параметрами не є взагалі.

Виміряно на живому 12.3.5: після запису `S Start = 0.12` маркер
`sample.start_marker` лишився нулем. Це не одна ручка з двома іменами, це
два незалежні контролі.

Синхронізуються сім властивостей: `start_marker`, `end_marker`, `gain`,
`warping`, `warp_mode`, `slicing_beat_division`,
`beats_granulation_resolution`. Усі три перевірені на запис наживо.

**Маркери задані в семплах, а не в долях і не в 0..1.** Тому стеля береться
з `sample.length` самого файлу: маркер за межами семплу відхиляється, бо
в партнера файл може бути іншим -- наприклад, ще не доїхав цілком.

Девайс адресується так само, як у `DeviceParamSet`: трек, `chain_path` і
сигнатура з ordinal. Тобто семпл на паді Drum Rack адресується через uuid
ланцюга пада, і це вже перевірено на живій парі.

Згортання за `sampleprop:<трек>:<ланцюги>:<девайс>:<властивість>` -- маркер
тягнуть мишею, тож серія доїжджає останньою, але `start_marker` не перекриває
`gain`. Лок береться на **девайс цілком**.

Девайса немає або в нього немає семплу -> подія мовчки не діє.

### Стоп-кнопка слота

```jsonc
{"type":"SlotStopButtonSet","payload":{
  "track":{"id":"…"},"scene":{"id":"…"},"value":false}}
```

Стоп-кнопка живе на **слоті**, а не на кліпі: вона є й у порожнього слота,
і саме порожній слот зі стоп-кнопкою зупиняє свій трек, коли запускають
сцену. Без неї трек продовжує грати те, що грав. Тобто це не косметика
Session-в'ю, а те, як сет звучить на переході між сценами.

Дебаунсу немає: це дискретний перемикач, один клац -- одна подія.
Згортання за `stopbtn:<track>:<scene>`, лока не потребує.

**Асиметрія знімка, названа прямо.** Подія ходить в обидва боки, тож під час
самої сесії пара сходиться точно. А от у знімку перелічені лише **вимкнені**
стоп-кнопки -- поле `stop_off` у треку, список uuid сцен. Причина в ціні:
ввімкнена кнопка -- стан Live за замовчуванням, і перелічувати кожен слот
означало б у сеті на 60 треків і 100 сцен шість тисяч подій на дрібницю.
Наслідок теж названий: знімок доводить партнера до вимкнених кнопок, але
не вмикає назад ті, що він вимкнув сам. Це свідомий вибір на користь
безпечного боку -- знімок нічого не вмикає навмання.

Слота за адресою немає -> подія мовчки не діє.

### Темп і метр сцени

```jsonc
{"type":"SceneTimingSet","payload":{
  "scene":{"id":"…"},
  "tempo_enabled":true,"tempo":140.0,
  "time_signature_enabled":true,
  "time_signature_numerator":6,"time_signature_denominator":8}}
```

**Увесь блок однією подією, а не пʼятьма.** Live віддає `-1` замість
значення, доки перевизначення вимкнене, тож поля взаємозалежні: писати
`tempo` при вимкненому `tempo_enabled` нікуди. Окремі події пройшли б
через саме такий стан. Та сама причина, що й у `ClipLoopSet`.

Порядок застосування незвертальний: спершу прапорець, потім значення.
Валідація -- повна й до першого запису: часткове застосування лишило б
сцену з увімкненим перевизначенням і чужим значенням, тобто гірше, ніж
до події.

Згортання за `scenetiming:<scene id>`, лок -- `scene:<id>:timing`: один
жест користувача дає одну подію, а різні сцени не заважають одна одній.

Чому це тир 1: сцена, що мовчки перемикає темп в одного і не перемикає
в іншого, розводить пару миттєво -- і виглядає це не як розсинхрон,
а як «у нього щось із Live».

### Властивості пісні

```jsonc
{"type":"SongPropSet","payload":{"prop":"signature_numerator","value":6}}
```

Одна подія на шість скалярів: `signature_numerator`, `signature_denominator`,
`clip_trigger_quantization`, `root_note`, `scale_name`, `scale_mode`.
Згортання за `song:<prop>`, тож розмір такту не перекриває тональність,
а серія рухів однієї властивості доїжджає останньою. Лок теж власний
на кожну: двоє можуть одночасно правити метр і тональність, і це не конфлікт.

**Чому це не косметика.** Без спільного розміру такту ті самі позиції нот
і меж кліпів означають у партнерів різне. Без спільної `clip_trigger_
quantization` той самий `ClipLaunch` спрацьовує в різний момент: у журналі
порядок ідеальний, а на слух розсинхрон.

Валідація одна на емісію і на прийом. `signature_denominator` приймається
лише степенем двійки -- Live інше мовчки округлить, і партнери розійдуться,
не помітивши. Після запису значення перечитується з LOM: Live міг клампнути.

Сюди ж належить **петля Arrangement** (`loop`, `loop_start`, `loop_length`)
і `punch_in`/`punch_out`. Петля -- це «де ми зараз працюємо», найспільніше,
що взагалі є в сеті; punch іде з нею, бо змінює саме те, що ця петля означає
для запису. Нульова довжина петлі відхиляється: Live підтягнув би її мовчки.

**Що НЕ синхронізується, і чому саме.**

| Властивість | Причина |
|---|---|
| `record_mode`, `session_record`, `arrangement_overdub` | Це намір людини натиснути запис, а не стан документа. Приїхавши, вони почали б писати озброєні треки партнера його ж входом -- чужий дубль як сюрприз |
| `back_to_arranger` | Стан **власного** відтворення, у кожного свій |
| `metronome` | Особиста річ, як гучність навушників |
| `midi_recording_quantization` | Впливає лише на власний запис: партнер дістає ноти вже квантованими, тож розсинхрону з неї не буває |

Невідома властивість відхиляється з назвою в тексті -- саме так партнер
дізнається, що його скрипт старіший, а не що «синхронізація не працює».

**Метроном і `midi_recording_quantization` не синхронізуються навмисно.**
Перший -- особиста річ, як гучність навушників. Друга впливає лише на
власний запис: партнер дістає ноти вже квантованими, тож розсинхрону з неї
не буває, а нав’язувати чужу сітку запису -- зайве.

У знімок властивості входять і розкладаються в `SongPropSet`: це частина
документа, а не смак.

### Семпли

```jsonc
{"type":"SampleLoad","payload":{
  "track":{"id":"…"},"scene":{"id":"…"},
  "target":{"kind":"slot"},
  "sample":{"path":"Samples/kick.wav","name":"kick.wav"}}}
```

**Подія несе адресу, а не байти.** Файли возить filesync окремим каналом
повз журнал: перескан `Samples/` раз на 10 секунд, маніфест за хешами,
партнер сам просить чого бракує.

Адреса -- **шлях відносно теки проєкту**. Це єдине, що портативне:
абсолютний шлях у партнера не існує, а Core Library адресується машинними
`FileId` (`query:Drums#FileId_5442` проти `FileId_6038` на іншій машині).
Вміст проєкту браузер натомість адресує шляхом --
`query:CurrentProject#Samples:kick.wav`, -- і саме туди filesync кладе файли.

Дві цілі, обидві через `browser.load_item` у **виділений** обʼєкт:

| `target.kind` | Адреса | Прицілювання |
|---|---|---|
| `slot` | `scene` в payload | `song.view.highlighted_clip_slot` |
| `drum_pad` | `device` + `chain_path?` + `note` | `device.view.selected_drum_pad` |
| `arrangement` | `clip.id` + `target.start_time` | тимчасовий слот + `duplicate_clip_to_arrangement` |

Прицілювання **пряме**: виміряно на 12.3.5, що семпл лягає саме на
виділений пад, а не на перший вільний. Довідник LOM позначає
`selected_drum_pad` як `R` -- це неправда, сеттер є (див. LOCAL-NOTES
скіла).

Для лінійки джерело збирається в порожньому слоті Session -- той самий
хід, що для MIDI в `ArrangementClipCreate`, тільки в тимчасовий кліп
вантажиться семпл. Кліп отримує той самий uuid, тож `ArrangementClipMove`
і `ArrangementClipDelete` працюють на ньому далі без змін.

**Audio-кліп в Arrangement структурної події не породжує взагалі.**
`ArrangementClipCreate` з `is_midi: false` приймальний бік чесно
відхиляє -- створити audio-кліп із нічого не можна. Тож емісія одразу
шле `SampleLoad`: партнер не відтворює структуру, він завантажує той
самий файл.

**Чому пади мають окремий шлях, а не гілку в дифі девайсів.** Семпл на
паді народжує **новий ланцюг** усередині рака, а нові контейнери дифф
девайсів навмисно пропускає -- інакше копія треку сипала б подіями на
кожен свій девайс. Наслідок виміряний на живому: сьогодні там повна тиша.
Якби ми зняли те правило, партнер натомість отримав би `DeviceInsert`
на голий `OriginalSimpler` -- девайс без звуку, тобто гірше за тишу.
Тому знімок падів (`адреса рака -> {нота: шлях}`) ведеться окремо.

Глушіння те саме, що в `DeviceLoad`: `load_item` рухає виділення, тож
без `_suppress_view` власний рух полетів би партнеру як присутність,
а створений кліп -- назад як подія.

**Подія може випередити файл**, і це нормальний стан, а не помилка:
filesync і журнал -- різні канали. Тому застосування чекає в черзі до
180 секунд, перевіряючи браузер на кожному тіку. Не дочекавшись --
каже вголос, який саме семпл не приїхав.

Семпл **поза текою проєкту** не анонсується взагалі: подія без портативної
адреси марна. Замість неї -- попередження з порадою `File > Collect All
and Save`, як і досі.

### Назви й кольори

`ObjectMetaSet` одразу синхронізує `name` або `color` для звичайного,
Return чи Master Track, Scene або Session Clip. Track адресується
своїм UUID/aux UUID, Scene — UUID сцени, а Clip — парою Track+Scene UUID.
`color` — ціле RGB-число `0x00rrggbb` в діапазоні `0..0xFFFFFF`;
Live вибирає найближчий колір зі своєї палітри.

### Параметри девайсів

`DeviceParamSet` покриває automatable-параметри девайсів звичайних, Return і Master
треків, рекурсивно включно з Rack `chains` і `return_chains`. Неперервні значення дебаунсяться на
200 мс, quantized-перемикачі та enum-и йдуть одразу. Кожне значення клампиться
локальними `min`/`max`; disabled-параметр не змінюється.

LOM не дає девайсу стабільного uuid, тому адреса складається з незмінної сигнатури
`class_name + class_display_name` та `ordinal` серед девайсів із тією самою
сигнатурою в поточному Track/Chain-контейнері. Параметр так само адресується оригінальним ім'ям (із fallback
на `name`) та ordinal серед тезок. Exact match обов'язковий: якщо на партнерській
машині немає відповідного плагіна або параметра, bridge пише warning і нічого не
змінює. Вставка однакового девайсу перед іншим однаковим девайсом може змінити
ordinal — це відома межа до появи синхронізації структури девайсів.

Активна playback-automation (`automation_state == 1`) не породжує мережевих подій:
інакше кожен automation tick потрапляв би в журнал. Ручний override
(`automation_state == 2`) вважається дією користувача й синхронізується.

Для вкладеного девайса `chain_path` несе UUID кожного Chain від зовнішнього до
внутрішнього. Bridge на кожному кроці перевіряє, що chain справді лежить у Rack
поточного parent-контейнера; невідомий чи розірваний nested path відхиляється, а
не застосовується в інший Chain. Сам цільовий device далі адресується сигнатурою
всередині останнього Chain.

Для звичайного треку `track` лишається старим `{id}`. Return і Master мають окремий
простір aux-ідентичності й передають `{id, kind: "return"}` або
`{id, kind: "master"}`. Bridge перевіряє і uuid, і kind, тому aux-подія не може
випадково застосуватися до звичайного треку чи іншого типу контейнера.

Нові `RegistryInit` містять `aux_tracks`: Return має locator `kind + idx + name`,
Master — лише `kind`, бо він singleton, а його UI-назва може бути локалізована.
UUID пишеться через Track `set_data` та в Song fallback-map. Для сесій, створених
до bridge 0.15 і тому без `aux_tracks`, UUID детерміновано виводиться з locator;
це дозволяє двом новим bridge приєднатися до старого журналу з однаковими id.

Нові `RegistryInit` містять записи Rack chains із parent-chain UUID та точним
bootstrap locator. Bridge пробує записати UUID на сам Chain через `set_data`, а
повну fallback-мапу завжди пише на Song. Для журналів, створених bridge до 0.14
і тому без `chains` у RegistryInit,
UUID детерміновано виводиться з track UUID + parent-chain + Rack signature +
chain kind/index/name. Однакові копії `.als` отримують однаковий migration ID.
Якщо конкретна версія Live персистить `Chain.set_data`, подальша позиція вже не
впливає на нього; інакше лишається слабший Song-map fallback.

У milestone 0.16 свідомо не входять створення, видалення, перейменування й
переставляння Return/Master/Rack/Chain/device структури. Структурні
зміни треба виконати однаково на обох машинах; mismatch дає warning/no-op.

Send адресується індексом, не uuid: у LOM це позиція в списку, прив'язана до
порядку return-треків. Поява чи зникнення return-треку змінює кількість send-ів
на кожному треку, тому `return_tracks` теж слухається — інакше нові send-и
лишились би німими.

`name` у посиланні на сцену необовʼязкове: у сцен Live за замовчуванням імені немає
(цифри в UI — це індекси). Немає імені — немає контрольної суми, і це видно з payload.

### MIDI-кліпи й нотні регіони

`ClipCreate` і `ClipDelete` синхронізують наявність MIDI-кліпу в Session View.
Audio clip creation цими подіями не передається. `ClipNotesSet` не пересилає
внутрішні `note_id`: вони локальні для конкретного екземпляра Live й потрібні лише
приймальному bridge, щоб видалити старі ноти перед додаванням нових.

Ноти діляться на детерміновані тайли: 4 долі за часом × 16 MIDI-висот. Payload
описує один тайл:

```jsonc
{
  "track": {"id": "..."},
  "scene": {"id": "..."},
  "clip": {"length": 8.0, "name": "Bass"},
  "region": {"from_pitch": 48, "pitch_span": 16, "from_time": 0.0, "time_span": 4.0},
  "notes": [{
    "pitch": 60, "start_time": 0.0, "duration": 1.0, "velocity": 108.0,
    "mute": false, "probability": 1.0, "velocity_deviation": 0.0,
    "release_velocity": 64.0
  }]
}
```

Застосування повністю замінює всі ноти, **початок** яких лежить у вказаному тайлі;
нота, що тягнеться за його праву межу, все одно належить тайлу свого `start_time`.
Різні тайли зливаються незалежно, а для одночасних правок одного тайла виграє
останній `global_seq`. Listener нот дебаунситься на 200 мс зі стелею 1 с.

Тайли суттєво зменшують UDP-повідомлення порівняно з snapshot усього кліпу, але
не дають математичної межі для патологічно щільного MIDI. Одна JSON-датаграма має
вміститись у 65 507 байтів; завеликий тайл bridge відкине й запише це в лог.

### Коалесинг: журнал несе дії, а не зміни LOM

LOM повідомляє про кожен крок значення, а не про жест. Без згортання один рух ручки
tempo дає ~20 подій, а запуск сцени — по одній події на кожен трек. Bridge згортає це
до відправки:

- **Неперервні параметри** (`tempo`, далі — mixer/device) дебаунсяться: подія йде
  через `DEBOUNCE_SEC` (200 мс) тиші після останньої зміни. Під час довгого
  безперервного жесту спрацьовує стеля `DEBOUNCE_MAX_HOLD` (1 с) — подія все одно
  йде, щоб довгий рух не пропав при розриві. Це той самий checkpoint, що в
  vision.md §5.5.
- **Зміни слотів** накопичуються до наступного тіку (`update_display`, ~100 мс).
  Якщо два і більше треків поїхали на той самий індекс сцени — це `SceneLaunch`,
  одна подія. Супутні зупинки треків без кліпу в цій сцені не відправляються:
  `scene.fire()` на приймальному боці відтворить їх сам. Якщо ж усе, що змінилось,
  зупинилось **і ніде більше нічого не грає** — це `StopAllClips`. Друга умова
  обовʼязкова: без неї дві зупинки поспіль в одному тіку виглядали б як глобальний
  стоп і заглушили б партнеру решту треків.

Затримка до ~100 мс на clip launch неважлива: Live і так квантизує запуск до межі такту.

### playing_slot_index нормалізується

У Live кілька відʼємних значень означають «не грає» (-1 — нічого, -2 — є fired slot).
Дзеркало зводить усі відʼємні до -1. Без цього перехід -1 → -2 читається як зміна
і породжує фантомний `ClipStop`, який у партнера застосується як `stop_all_clips()`
і заглушить йому треки, яких дія взагалі не стосувалась.

### Адресація об'єктів — стабільні uuid

Треки і сцени адресуються **uuid**, не індексом. Індекс зсувається від вставки
треку; uuid — ні. `name` у посиланні лишається тільки для читабельності логів
і ні на що не впливає.

Bridge тримає реєстр `uuid → пряме посилання на LOM-об'єкт`. Посилання переживає
зсув індексів, бо Python тримає сам об'єкт, а не позицію. Видалений у Live об'єкт
лишається в реєстрі, але звертання до нього кидає `RuntimeError` → `obj_of()`
повертає `None` → подія тихо ігнорується. Це і є tombstone з vision.md §5.6,
отриманий безкоштовно з семантики самого Live.

### Бутстрап реєстру

Реєстр — це **подія в журналі**, а не стан relay: джерело правди одне (vision.md §2).

1. Клієнт заходить, `welcome` містить `registry` — payload наявного `RegistryInit`
   або `null`. Він приходить окремо від хвоста журналу, бо клієнт після рестарту
   має високий `since` і `RegistryInit` у хвіст уже не потрапляє.
2. `registry: null` → daemon просить bridge `registry_build`; той видає uuid усім
   об'єктам і повертає мапу, яка йде в журнал як `RegistryInit`.
3. `registry` є → daemon віддає його bridge як `registry_adopt`. Той спершу піднімає
   uuid із `.als`: об'єкт, що вже носить потрібний uuid, впізнає себе сам, і ні
   позиція, ні ім'я значення не мають. Лише для решти працює фолбек **за позицією
   зі звіркою імені** — єдине місце, де індекс ще виступає адресою.
4. Незіставлені об'єкти логуються; події на них не застосуються. Проєкти розійшлись —
   це видно одразу, а не мовчазним застосуванням не туди.

Звірка за іменем лишається строгою саме тому, що спрацьовує лише для об'єктів без
збереженого uuid. Пом'якшити її не можна: там, де впізнавання не спрацювало, позиція —
єдиний сигнал, і зв'язати за нею об'єкти з різних проєктів гірше, ніж не зв'язати.

**Сесія relay прив'язана до проєкту.** `RegistryInit` описує конкретний набір
об'єктів; відкрити під тією ж `--session` інший `.als` означає, що не зіставиться
нічого. Bridge це проговорює окремим warning — новому проєкту потрібна нова сесія.

### Персистентність: uuid живуть у самому .als

`Song.set_data` / `get_data` зберігають довільні дані **всередині файлу проєкту**.
Bridge кладе uuid на кожен об'єкт окремо (`obj.set_data("abletonmp_id", …)`), тож
ідентичність переживає і переставляння треків, і копіювання `.als` на іншу машину.

**Обидва механізми працюють разом, а не замість одного.** Перевірено на Live 12.3.8:
`Track` має `set_data`, а `Scene` — **ні** (`hasattr` дає `False`), тож сцени в
принципі не можуть носити uuid на собі. Мапа на `Song` пишеться завжди — і як
покриття для таких об'єктів, і щоб не залежати від того, чи відрізняється
відсутній метод від методу, що мовчки нічого не зберігає.

При відновленні спершу опитуються самі об'єкти, потім мапа добирає тих, хто себе не
впізнав. Мапа прив'язана до позицій, тож для сцен ідентичність між сесіями слабша:
переставляння сцен її зламає. Для треків — ні.

Sidecar-файл поруч із проєктом свідомо відкинуто: `song.file_path` порожній, доки
сет не збережено, тобто саме на старті нового проєкту такий файл нікуди класти.

Порядок на бутстрапі:

1. `_restore_registry()` піднімає uuid із `.als`. Дві машини, що відкрили той самий
   файл, отримують однакові uuid ще до будь-якого обміну — зіставлення за позиціями
   стає фолбеком, а не основним шляхом.
2. Ті об'єкти, у яких збереженого uuid не було, отримують новий.
3. Після будь-якої зміни реєстру (бутстрап, adopt, create/delete) uuid пишуться
   назад у `.als`. Канонічним лишається той, що ліг у журнал: `adopt` перезаписує
   локальні значення.

Побічний ефект: запис у `.als` позначає сет зміненим, і Live спитає про збереження
при закритті. Без збереження uuid до наступної сесії не доживуть.

### Реєстр живий після бутстрапу

`tracks`/`scenes`-listener звіряє реєстр із деревом Live при кожній зміні структури.
Нові об'єкти отримують uuid і йдуть у журнал як `TrackCreate`/`SceneCreate`
(з `idx` і `kind`, бо партнер має створити той самий об'єкт, а не абищо); зниклі —
як `TrackDelete`/`SceneDelete`.

`idx` тут не адреса, а побажання позиції при створенні: адресою лишається uuid.
Якщо позиція некоректна, об'єкт створюється в кінці.

Обидві операції ідемпотентні: `TrackCreate` на вже відомий uuid не створює дубль,
`TrackDelete` на вже видалений — no-op. Тобто повторне застосування після реконнекту
безпечне.

Поки застосовується чужа структурна подія, власний listener мовчить
(`_suppress_struct`) — інакше створений трек одразу поїхав би назад як власний
`TrackCreate`. Якщо listener усе ж спрацював усередині виклику LOM і встиг видати
новому треку свій uuid, наступний `bind()` це перезапише: реєстр самолікується.

Гонка одночасного конекту вирішується без логіки власника сесії: обидва бачать
порожній журнал, обидва сабмітять `RegistryInit`, relay комітить перший і відхиляє
другий, і програвший приймає переможця звичайним `commit`.

До завершення бутстрапу bridge не відправляє подій із посиланнями на об'єкти —
партнер однаково не зміг би їх зарезолвити. `TransportSet` і `TempoSet` не залежать
від реєстру і ходять одразу.

### Echo suppression

Bridge тримає дзеркало останніх відомих значень (`playing`, `tempo`,
`playing_slot_index` по треках). Listener породжує подію **лише якщо значення
відрізняється від дзеркала**. Перед застосуванням чужої команди bridge записує
очікуване значення в дзеркало, тож listener, що спрацює після запису в LOM,
нічого не відправить.
