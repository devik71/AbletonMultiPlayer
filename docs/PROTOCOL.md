# Протокол (фаза 1)

Три шари, два хопи. Bridge живе в процесі Live, daemon — окремий процес на тій самій
машині, relay — один на сесію.

```
Live (LOM)  ⇄  Bridge (Remote Script, Python)
                    ⇅  JSON over UDP, localhost
               Daemon (Node)
                    ⇅  JSON over WebSocket
                Relay / Sequencer (Node)
```

## 1. Bridge ⇄ Daemon — JSON over UDP

Один JSON-об'єкт на датаграму, UTF-8, без роздільників. Тільки localhost.

| Напрям | Порт |
|---|---|
| daemon слухає (bridge → daemon) | `19845` |
| bridge слухає (daemon → bridge) | `19846` |

### Bridge → Daemon

```jsonc
{"m":"hello","live":"12.3.8","script":"0.1.0","pid":1234}
{"m":"bye"}
{"m":"heartbeat","t":1723000000.0}
{"m":"event","type":"TransportSet","payload":{"playing":true},"lseq":7}
{"m":"snapshot","state":{"tempo":128.0,"playing":false,"tracks":[...]}}
{"m":"log","level":"warn","text":"..."}
```

### Daemon → Bridge

```jsonc
{"m":"apply","type":"TransportSet","payload":{"playing":true},"gseq":42}
{"m":"snapshot_request"}
{"m":"registry_build"}
{"m":"registry_adopt","registry":{"tracks":[...],"scenes":[...]}}
{"m":"ping","t":1723000000.0}
```

У відповідь на `registry_build` bridge шле `{"m":"registry","registry":{...}}`.

`apply` — команда застосувати чужу (вже впорядковану сервером) подію до LOM.
Bridge при цьому оновлює last-known-value **до** запису в LOM, щоб власний listener
не породив ехо-подію (див. §4).

## 2. Daemon ⇄ Relay — JSON over WebSocket

### Client → Relay

```jsonc
{"m":"join","session":"default","author":"p1","since":0,"proto":1}
{"m":"submit","event":{"type":"TempoSet","payload":{"bpm":128},"author":"p1","lseq":7,"ts":1723000000.0}}
{"m":"ping","t0":1723000000.0}
```

`since` — останній `gseq`, який клієнт уже має. Relay дошле хвіст.

### Relay → Client

```jsonc
{"m":"welcome","author":"p1","session":"default","head":{"gseq":41,"hash":"ab12..."},"peers":["p2"]}
{"m":"commit","event":{...,"gseq":42,"prev_hash":"ab12...","hash":"cd34..."}}
{"m":"peers","peers":["p1","p2"]}
{"m":"pong","t0":...,"t1":...,"t2":...}
{"m":"error","code":"proto_mismatch","text":"..."}
```

### Clock sync

Класична NTP-схема. `t0` — час відправки клієнтом, `t1` — прийому сервером,
`t2` — відправки сервером, `t3` — прийому клієнтом.

```
offset = ((t1 - t0) + (t2 - t3)) / 2
rtt    =  (t3 - t0) - (t2 - t1)
```

## 3. Журнал і hash-chain

Relay пише `journal.jsonl` — один закомічений івент на рядок. Кожен івент:

```jsonc
{
  "gseq": 42,              // монотонний, присвоює виключно relay
  "prev_hash": "ab12...",  // hash попереднього івента ("" для gseq=1)
  "hash": "cd34...",       // sha256(prev_hash + canonical_json(body))
  "type": "TempoSet",
  "payload": {"bpm": 128},
  "author": "p1",
  "lseq": 7,               // локальна послідовність автора, для дедуплікації
  "ts": 1723000000.0,      // wall-clock автора, довідково; НЕ впливає на порядок
  "srv_ts": 1723000000.2   // wall-clock relay
}
```

`canonical_json` — ключі відсортовані, без пробілів. Поля `hash` немає в тілі,
яке хешується.

Дедуплікація на relay: пара `(author, lseq)` вже бачена → івент ігнорується
(ідемпотентний ре-сабміт після реконнекту).

## 4. Типи подій (фаза 1)

| Type | Payload | Apply у LOM |
|---|---|---|
| `RegistryInit` | `{tracks: [{id, idx, name}], scenes: [...]}` | — (бутстрап, див. нижче) |
| `TransportSet` | `{playing: bool}` | `song.start_playing()` / `stop_playing()` |
| `TempoSet` | `{bpm: float}` | `song.tempo = bpm` |
| `ClipLaunch` | `{track: {id, name}, scene: {id, name?}}` | `clip_slots[j].fire()` |
| `ClipStop` | `{track: {id, name}}` | `track.stop_all_clips()` |
| `SceneLaunch` | `{scene: {id, name?}}` | `scenes[j].fire()` |
| `StopAllClips` | `{}` | `song.stop_all_clips()` |
| `TrackCreate` | `{track: {id, name}, idx, kind: "midi"\|"audio"}` | `create_midi_track(i)` / `create_audio_track(i)` |
| `TrackDelete` | `{track: {id}}` | `song.delete_track(i)` |
| `SceneCreate` | `{scene: {id, name?}, idx}` | `song.create_scene(i)` |
| `SceneDelete` | `{scene: {id}}` | `song.delete_scene(i)` |

`name` у посиланні на сцену необовʼязкове: у сцен Live за замовчуванням імені немає
(цифри в UI — це індекси). Немає імені — немає контрольної суми, і це видно з payload.

### Коалесинг: журнал несе дії, а не зміни LOM

LOM повідомляє про кожен крок значення, а не про жест. Без згортання один рух ручки
tempo дає ~20 подій, а запуск сцени — по одній події на кожен трек. Bridge згортає це
до відправки:

- **Неперервні параметри** (`tempo`, далі — mixer/device) дебаунсяться: подія йде
  через `DEBOUNCE_SEC` (200 мс) тиші після останньої зміни. Під час довгого
  безперервного жесту спрацьовує стеля `DEBOUNCE_MAX_HOLD` (1 с) — подія все одно
  йде, щоб довгий рух не пропав при розриві. Це той самий checkpoint, що в
  vision.md §5.5.
- **Зміни слотів** накопичуються до наступного тіку (`update_display`, ~100 мс).
  Якщо два і більше треків поїхали на той самий індекс сцени — це `SceneLaunch`,
  одна подія. Супутні зупинки треків без кліпу в цій сцені не відправляються:
  `scene.fire()` на приймальному боці відтворить їх сам. Якщо ж усе, що змінилось,
  зупинилось **і ніде більше нічого не грає** — це `StopAllClips`. Друга умова
  обовʼязкова: без неї дві зупинки поспіль в одному тіку виглядали б як глобальний
  стоп і заглушили б партнеру решту треків.

Затримка до ~100 мс на clip launch неважлива: Live і так квантизує запуск до межі такту.

### playing_slot_index нормалізується

У Live кілька відʼємних значень означають «не грає» (-1 — нічого, -2 — є fired slot).
Дзеркало зводить усі відʼємні до -1. Без цього перехід -1 → -2 читається як зміна
і породжує фантомний `ClipStop`, який у партнера застосується як `stop_all_clips()`
і заглушить йому треки, яких дія взагалі не стосувалась.

### Адресація об'єктів — стабільні uuid

Треки і сцени адресуються **uuid**, не індексом. Індекс зсувається від вставки
треку; uuid — ні. `name` у посиланні лишається тільки для читабельності логів
і ні на що не впливає.

Bridge тримає реєстр `uuid → пряме посилання на LOM-об'єкт`. Посилання переживає
зсув індексів, бо Python тримає сам об'єкт, а не позицію. Видалений у Live об'єкт
лишається в реєстрі, але звертання до нього кидає `RuntimeError` → `obj_of()`
повертає `None` → подія тихо ігнорується. Це і є tombstone з vision.md §5.6,
отриманий безкоштовно з семантики самого Live.

### Бутстрап реєстру

Реєстр — це **подія в журналі**, а не стан relay: джерело правди одне (vision.md §2).

1. Клієнт заходить, `welcome` містить `registry` — payload наявного `RegistryInit`
   або `null`. Він приходить окремо від хвоста журналу, бо клієнт після рестарту
   має високий `since` і `RegistryInit` у хвіст уже не потрапляє.
2. `registry: null` → daemon просить bridge `registry_build`; той видає uuid усім
   об'єктам і повертає мапу, яка йде в журнал як `RegistryInit`.
3. `registry` є → daemon віддає його bridge як `registry_adopt`; той накладає чужі
   uuid на свої об'єкти **за позицією, звіряючи імена**. Це єдине місце, де індекс
   ще працює адресою — одноразово, на бутстрапі.
4. Незіставлені об'єкти логуються; події на них не застосуються. Проєкти розійшлись —
   це видно одразу, а не мовчазним застосуванням не туди.

### Персистентність: uuid живуть у самому .als

`Song.set_data` / `get_data` зберігають довільні дані **всередині файлу проєкту**.
Bridge кладе uuid на кожен об'єкт окремо (`obj.set_data("abletonmp_id", …)`), тож
ідентичність переживає і переставляння треків, і копіювання `.als` на іншу машину.
Якщо об'єкти не приймають `set_data`, є фолбек: одна мапа на `Song`, прив'язана до
позицій — слабший варіант, бо ламається від переставляння між сесіями.

Sidecar-файл поруч із проєктом свідомо відкинуто: `song.file_path` порожній, доки
сет не збережено, тобто саме на старті нового проєкту такий файл нікуди класти.

Порядок на бутстрапі:

1. `_restore_registry()` піднімає uuid із `.als`. Дві машини, що відкрили той самий
   файл, отримують однакові uuid ще до будь-якого обміну — зіставлення за позиціями
   стає фолбеком, а не основним шляхом.
2. Ті об'єкти, у яких збереженого uuid не було, отримують новий.
3. Після будь-якої зміни реєстру (бутстрап, adopt, create/delete) uuid пишуться
   назад у `.als`. Канонічним лишається той, що ліг у журнал: `adopt` перезаписує
   локальні значення.

Побічний ефект: запис у `.als` позначає сет зміненим, і Live спитає про збереження
при закритті. Без збереження uuid до наступної сесії не доживуть.

### Реєстр живий після бутстрапу

`tracks`/`scenes`-listener звіряє реєстр із деревом Live при кожній зміні структури.
Нові об'єкти отримують uuid і йдуть у журнал як `TrackCreate`/`SceneCreate`
(з `idx` і `kind`, бо партнер має створити той самий об'єкт, а не абищо); зниклі —
як `TrackDelete`/`SceneDelete`.

`idx` тут не адреса, а побажання позиції при створенні: адресою лишається uuid.
Якщо позиція некоректна, об'єкт створюється в кінці.

Обидві операції ідемпотентні: `TrackCreate` на вже відомий uuid не створює дубль,
`TrackDelete` на вже видалений — no-op. Тобто повторне застосування після реконнекту
безпечне.

Поки застосовується чужа структурна подія, власний listener мовчить
(`_suppress_struct`) — інакше створений трек одразу поїхав би назад як власний
`TrackCreate`. Якщо listener усе ж спрацював усередині виклику LOM і встиг видати
новому треку свій uuid, наступний `bind()` це перезапише: реєстр самолікується.

Гонка одночасного конекту вирішується без логіки власника сесії: обидва бачать
порожній журнал, обидва сабмітять `RegistryInit`, relay комітить перший і відхиляє
другий, і програвший приймає переможця звичайним `commit`.

До завершення бутстрапу bridge не відправляє подій із посиланнями на об'єкти —
партнер однаково не зміг би їх зарезолвити. `TransportSet` і `TempoSet` не залежать
від реєстру і ходять одразу.

### Echo suppression

Bridge тримає дзеркало останніх відомих значень (`playing`, `tempo`,
`playing_slot_index` по треках). Listener породжує подію **лише якщо значення
відрізняється від дзеркала**. Перед застосуванням чужої команди bridge записує
очікуване значення в дзеркало, тож listener, що спрацює після запису в LOM,
нічого не відправить.
